What MCP Actually Is, Briefly

This course's soft prerequisite, mcp-for-everyone, spends eight full chapters on the Model Context Protocol — what it is, how a server exposes tools and resources, how a client discovers and calls them, transports, permissions, prompt injection risk in tool output, testing, and production hardening. This chapter does not re-teach any of that. If MCP itself is new to you — the actual protocol mechanics, not just "it's a way to expose tools" — go read that course's Chapters 1 through 8 first; this chapter assumes you already know what a resource is, what a transport is, and what a tool schema looks like from the protocol's side. What follows is the shortest useful summary, enough to place today's code in context, not a substitute for that material.

What is... MCP, in one paragraph? The Model Context Protocol is a standard way to expose tools (and other capabilities — resources, prompts) to a model-calling client, independent of which specific application is doing the calling. A server implements a tool once; any MCP-speaking client — a chat app, an IDE integration, or (as of this chapter) this course's own agent — can discover and call that same tool without the tool's author writing separate integration code for each one. The practical shift from everything Chapters 7 and 8 built: those tools only ever existed as Python functions inside this course's own files. An MCP server's tools exist independent of any one client, meant to be connected to and reused.

Concretely for this chapter: mcp_git_server.py (read it — it's short) implements git_status and git_diff exactly once, using the mcp Python SDK's server-side decorator API. Nothing about that file knows or cares that this course's particular agent is the one calling it. A completely different agent, written in a different language, using a different loop shape entirely, could connect to the exact same server process and get the exact same two tools, with zero changes to mcp_git_server.py.

Why This Matters for THIS Agent, Concretely

Chapter 8 closed with a direct question worth sitting with before writing any code: what does a given tool's worst-case bad call look like, and who's responsible for scoping it? That question doesn't go away when a tool moves behind MCP — but a second, genuinely new question joins it: does re-implementing this specific tool, per project, actually buy anything? For read_file/write_file/edit_file, the honest answer is no — they're tightly coupled to this exact agent's WORKSPACE boundary and _safe_path() check, and there's no meaningful "shared, reusable read_file server" worth depending on for that. For git_status/ git_diff, the answer flips: they're generic (any agent working in any git repository needs the same two commands), they're read-only (low blast radius if the server itself has a bug), and hand-writing the same subprocess.run(["git", "status", "--porcelain"], ...) call inside every new agent this course — or you — ever builds is pure duplication with no upside. That's the concrete case for MCP here, not an abstract "protocols are good" argument: two specific tools that are generic enough and safe enough to be worth getting from one shared place instead of retyping.

The Real Integration Work: Bridging MCP Into TOOLS/dispatch_tool_call

Here's the part that isn't obvious from "MCP exposes tools" alone: this course's agent, since Chapter 7, is built against the plain openai client's TOOLS/tool_calls shape — a list of {"type": "function", "function": {...}} schemas, a model response with message.tool_calls, dispatch by looking up a name in a dict. MCP's client-side API is a different shape entirely: a Client connection, an await client.list_tools() call returning MCP's own Tool objects, and await client.call_tool(name, args) returning an MCP-specific result object. Nothing about this pairs up automatically — something has to translate between the two.

Where this pattern comes from The Client / await client.list_tools() / await client.call_tool(name, args) shape below — and reading result.tools, result.is_error, result.content[0].text, result.structured_content off the results — is drawn directly from mcp-for-everyone Chapter 7 ("Building an MCP Client/Host") and Chapter 8 ("Connecting Multiple Servers"); both of that course's reference solutions use exactly this shape. That's reused, verified knowledge, not re-derived here. One piece genuinely is new: those two chapters connect to their MCP server in-process (Client(mod.mcp), importing the server module directly). This chapter's server is a real, separate, standalone process, launched over the stdio transport — a different corner of the same mcp package (StdioServerParameters, stdio_client), verified independently against the actually-installed mcp 2.0.0 package this session, not sourced from mcp-for-everyone's in-process examples.

There's a second, less obvious mismatch: MCP's client API is async throughout. This course's run_agent loop has been plain synchronous code since Chapter 7, and this chapter is explicit that it stays that way — rewriting the loop to async def everywhere just to accommodate one tool source would be exactly backwards, letting an implementation detail of one tool's origin leak into code that has nothing to do with tools at all. The fix is a small bridge class, MCPBridge, that keeps one persistent MCP client connection alive on a background thread's own event loop and exposes plain, blocking, synchronous methods — list_tools(), call_tool() — that dispatch_tool_call can call exactly like any other function, no await anywhere in the loop:

the shape of the bridge, abbreviated -- full version in project/solution.py 
class MCPBridge:
    """One persistent MCP client connection, on a background thread's
    own event loop, exposed through plain synchronous methods."""

    def __init__(self, command, args):
        self._requests = queue.Queue()
        self._loop = asyncio.new_event_loop()
        self._thread = threading.Thread(target=self._run_loop, args=(command, args), daemon=True)
        self._thread.start()
        # ... waits for the connection to actually be ready before returning

    async def _worker(self, command, args):
        from mcp import Client, StdioServerParameters, stdio_client
        params = StdioServerParameters(command=command, args=args)
        async with Client(stdio_client(params)) as client:
            while True:
                kind, payload, result_q = await self._loop.run_in_executor(None, self._requests.get)
                if kind == "list_tools":
                    result = await client.list_tools()
                    result_q.put(("ok", result.tools))
                elif kind == "call_tool":
                    name, call_args = payload
                    result = await client.call_tool(name, call_args)
                    result_q.put(("ok", result.content[0].text if result.content else str(result.structured_content)))

    def list_tools(self):
        return self._call("list_tools")     # blocks, returns a plain value

    def call_tool(self, name, args):
        return self._call("call_tool", (name, args))

One implementation detail worth naming, because it's the kind of bug that only shows up once you actually run this: an earlier, more "obvious" version of this class scheduled the client's connect and disconnect as two separately-scheduled coroutines on the same event loop, and it raised a real error from the anyio library underneath MCP's stdio transport — "Attempted to exit cancel scope in a different task than it was entered in." anyio's task groups tie a cancel scope to the specific async task that opened it, and two separately-scheduled coroutines still count as two different tasks even on the same loop. The fix used above: the client's entire connected lifetime runs inside one coroutine (_worker), and the background thread only ever talks to it through a thread-safe queue, never re-entering the async with block from a separate call. This is exactly the kind of thing you only find by actually running code against a real installed package, not by reasoning about async Python in the abstract — the same discipline this course's own build process has followed since Chapter 7.

With that bridge in place, connect_git_tools() does the actual translation this section opened with — turning MCP's tool metadata into this course's schema shape:

MCP tool metadata -> this course's TOOLS shape 
def connect_git_tools():
    bridge = MCPBridge(sys.executable, [GIT_SERVER_SCRIPT])
    tools = bridge.list_tools()   # a list of MCP Tool objects

    for t in tools:
        # workspace is harness-injected, never shown to the model --
        # the MCP-flavored version of Chapter 8's _safe_path boundary
        schema = dict(t.input_schema)
        properties = {k: v for k, v in schema.get("properties", {}).items() if k != "workspace"}
        required = [r for r in schema.get("required", []) if r != "workspace"]
        schema = {**schema, "properties": properties, "required": required}

        TOOLS.append({
            "type": "function",
            "function": {"name": t.name, "description": t.description, "parameters": schema},
        })
        MCP_TOOL_NAMES.add(t.name)

And dispatch_tool_call gains exactly one new branch — everything else in it is byte-for-byte Chapter 8's version:

one new branch, nothing else touched 
if name in TOOL_FUNCTIONS:
    return TOOL_FUNCTIONS[name](**args)   # unchanged from Chapter 8

if name in MCP_TOOL_NAMES:                # NEW
    full_args = {**args, "workspace": WORKSPACE}   # harness injects it back

Notice the workspace argument's round trip: stripped out of the schema the model sees in connect_git_tools(), injected back in by the harness right before the MCP call in dispatch_tool_call. The model never sets it, never sees it, and has no way to get it wrong — the exact same what-the-model-controls-versus-what-the-harness-enforces line Chapter 7's _safe_path drew for local file paths, applied here to an argument that happens to cross a protocol boundary instead of just a function call.

What Changes and What Doesn't

Say this plainly, because it's the single most important fact in this chapter: run_agent — the entire plan/act/observe/repeat loop, unchanged since Chapter 7 — does not change at all. Not one line. It calls client.chat.completions.create(...), checks msg.tool_calls, calls dispatch_tool_call, appends the result, repeats. It has no idea, and needs no idea, whether a given tool call is about to run a local Python function or trigger an MCPBridge.call_tool() round trip to a separate process. That decision was already made, once, before the loop ever runs — inside connect_git_tools() and the one new branch in dispatch_tool_call.

What did change, concretely: TOOLS is no longer a single fixed list defined once at the top of the file — it's built partly at startup, from a live server's own description of itself, instead of entirely hand-typed. And TOOL_FUNCTIONS genuinely lost two entries — there is no git_status Python function in this agent's process anymore, on purpose. Both of those are real, meaningful changes to how this agent is assembled. Neither one required touching the mechanism Chapters 4 through 7 spent six chapters establishing.

Honest Trade-Offs: When Hand-Rolled Is Still Right

MCP tools are not a strict upgrade over hand-rolled ones, and this chapter isn't claiming they are. Getting a tool from an MCP server instead of writing it locally trades one specific set of costs for one specific set of benefits, and both sides are real:

What is... the actual cost of the MCP swap, stated without overselling the benefit? What you gain: the tool's implementation is written once and reusable across any MCP-speaking client, not just this one agent — real for genuinely generic, low-blast-radius tools like read-only git commands. What you pay: a running server process that has to actually be there (this chapter's connect_git_tools() treats a missing or unreachable server as non-fatal for exactly this reason — see below); a client connection that has to be opened, kept alive, and cleanly closed, which is real code (MCPBridge, above) that a local function call never needed; a real latency cost — a subprocess round trip and a protocol message, not a direct in-process function call — that's negligible for git_status but wouldn't be free for something called on every single loop step; and a whole new failure mode class (the server crashes, the connection drops mid-run, a schema mismatch between what the server reports and what actually executes) that a hand-rolled tool structurally cannot have, because there's no separate process to fail.

This is exactly why connect_git_tools()'s failure path is a graceful False return, not a crash — losing git_status/git_diff for one run because a server didn't start is a real capability loss, but it's not a reason to abort a task that might not have needed git tools anyway, and it would be a strange trade if adding MCP integration made this agent less reliable than Chapter 8's version whenever the MCP server happened to be down. The same graceful-degradation posture this course has used since Chapter 7 for a missing openai package or an unreachable Ollama server applies here too, one layer further out.

So: when is hand-rolled still the right call? When a tool is tightly coupled to this specific agent's own state — read_file/write_file/edit_file are inseparable from _safe_path() and this exact agent's WORKSPACE boundary; there's no meaningful "generic file-editing MCP server" that wouldn't just be reinventing that same boundary somewhere else, worse, further away from the code that needs to enforce it. When the tool's whole point is running arbitrary, caller-composed input — run_shell_command exists to run whatever command string the model composes; there's no "shared run-any-shell-command server" worth depending on, because the tool has no fixed behavior to standardize in the first place. When latency actually matters — a tool called on nearly every loop step is a worse candidate for a network/subprocess round trip than one called occasionally. And MCP is worth it when a tool is generic, reusable across more than one agent or project, and low-blast-radius enough that a connection failure or a compromised server isn't catastrophic — exactly the profile git_status/ git_diff fit, and exactly why this chapter picked those two specifically, not run_shell_command.

GenAI Builder Thought Process

Problem: a developer hears "MCP" and reaches for it as the default way to add any new tool going forward, treating "it's an MCP server" as inherently safer or more professional than a local function, independent of what the tool actually does.

Assumption being made: that moving a tool behind a protocol is itself a safety or quality improvement — the same category of mistake as assuming "more tools" is inherently good or bad news, which Chapter 8's own closing section already named directly.

What actually distinguishes it: MCP changes where a tool's implementation lives and how many clients can reuse it. It does not automatically change whether the tool is safe, whether its worst-case bad call is loud or silent, or whether it's the right tool for the job at all — a poorly-scoped tool exposed over MCP is still a poorly-scoped tool, now with an extra network hop and a connection to manage. This chapter's actual criteria for reaching for MCP were narrow and specific: generic, reusable, low-blast-radius. run_shell_command fails all three, and moving it behind MCP wouldn't have made it safer — it would have added a process boundary around the exact same unscoped risk Chapter 8 already named honestly.

Why this matters closing Module 3: the question this whole module has circled back to at every tool layer decision — Chapter 8's "what's the worst-case bad call, and is it loud or silent," this chapter's "does sharing this tool actually buy anything" — isn't a checklist item you finish and move past. It's the actual judgment call every new tool needs, whether it's a three-line local function or a full MCP server, for the rest of this course and past it.

Working definition to carry forward: MCP is a mechanism for sharing a tool's implementation across clients, not a safety property. Deciding whether a given tool belongs behind MCP or hand-rolled locally is a design judgment — generic versus agent-specific, reusable versus one-off, low-blast-radius versus high — made the same way every other tool-layer decision in this module was made: by asking what the tool actually does on a bad call, not by which mechanism sounds more sophisticated.

Points To Remember — Closing Module 3

  • MCP is a standard protocol for exposing tools (and other capabilities) to a model-calling client, independent of which specific application is calling — a tool implemented once as an MCP server can be reused by any MCP-speaking client, unlike a hand-rolled tool that only ever exists inside one project's own files. This course's soft prerequisite, mcp-for-everyone (Chapters 1-8), covers the protocol itself in depth; this chapter deepens that knowledge for one specific use, it doesn't re-teach it.
  • Bridging an MCP server's tools into this course's TOOLS/TOOL_FUNCTIONS shape required two real pieces of new work: converting MCP's own tool metadata into this course's schema shape (connect_git_tools()), and bridging MCP's inherently async client API into a synchronous loop without rewriting the loop (MCPBridge, running one persistent connection on a background thread's event loop, exposed as plain blocking methods).
  • run_agent — the entire plan/act/observe/repeat loop — did not change at all since Chapter 7. Only where dispatch_tool_call's lookup actually goes changed: a local Python function call for TOOL_FUNCTIONS entries, an MCPBridge.call_tool() round trip for MCP_TOOL_NAMES entries.
  • MCP tools trade a real, concrete set of costs (a running server process, a connection to open and manage, real latency, a new class of connection-failure modes) for reuse and standardization. Worth it for tools that are generic, reusable across more than one agent, and low-blast-radius — git_status/git_diff here. Not worth it for tools tightly coupled to this specific agent's own state (read_file/write_file/edit_file's _safe_path() boundary) or whose entire point is running arbitrary caller-composed input (run_shell_command).
  • A harness-injected argument (workspace) that the model never sees or sets, stripped from the schema and reinjected right before the call, is the same what-the-model-controls-versus-what-the-harness-enforces boundary Chapter 7's _safe_path established — applied here across a protocol boundary instead of just a function call.
  • Module 3, closed: Chapter 7 built the loop and proved the mechanism worked with three tools. Chapter 8 went deep on the tool layer — five tools, each with real, specific failure-mode design. This chapter went wide on tool portability — the same loop, the same dispatch shape, now able to reach tools it doesn't implement itself.
