Chapter 7 Exercises ~35 min

Exercises: Build: A Minimal Coding Agent

This chapter's exercises don't need a running Ollama server to verify — starter.py and solution.py in this folder test the tool-dispatch logic and the loop's stop-condition control flow with mocked/scripted turns instead of a live model, so every exercise below is checkable by running the file directly.

Exercise standard Six tasks below. At least three are production-gear: harder, ambiguous, real-world judgment calls rather than clean textbook cases.

1 Implement dispatch_tool_call

Open starter.py. Fill in TODOs 1 through 4 inside dispatch_tool_call: parse the JSON arguments string, look up the right tool function, check every required argument is present, and call it — returning a descriptive error string instead of raising for each failure case. Run python3 starter.py and get the first five checks to PASS.

2 Implement run_loop_stub

Fill in TODOs 1 through 4 inside run_loop_stub: walk through a list of scripted "model turns," stop cleanly the moment a turn has no tool call, and stop at the step cap otherwise — exactly Chapter 4's clean stop and hard stop, driven by mocked data instead of a real model call. Get the remaining three checks to PASS.

3 Trace a real failure by hand

Without running any code, write out, step by step, what dispatch_tool_call("read_file", "{not valid json") actually returns and why — name each line of your implementation that gets triggered, in order. Then run it and confirm your trace was right. This is the same discipline Chapter 4's project had you apply to a real transcript, now applied to code you wrote yourself.

4 (Production-gear) Add a third tool to the dispatch table

Add a new tool function delete_file(path) to starter.py that removes a key from FAKE_DISK (or returns an error string if the key doesn't exist), register it in both TOOL_FUNCTIONS and REQUIRED_ARGS, and add at least two new test cases to main() — one well-formed call and one missing-argument call — without changing dispatch_tool_call's own logic at all. If you have to modify dispatch_tool_call to make your new tool work, that's a sign that function isn't actually general-purpose yet; note what you had to change and why.

5 (Production-gear) Construct a step-cap-at-exactly-N scenario

Using run_loop_stub, construct a scripted_turns list and a max_steps value such that the loop hits the step cap on exactly step 3, not step 1 and not step 5. Before running it, write down your prediction of the exact return value and why. Then verify. This is deliberately more finicky than task 2's tests — off-by-one mistakes in loop-boundary logic are a real, common class of bug in actual agent harnesses, not just a classroom exercise.

6 (Production-gear) Review your own dispatch function like Chapter 3 taught

The lesson's project/solution.py has a list_files tool with a real boundary-escape bug: it doesn't confine its path argument to a safe root the way the other tools do. Your dispatch_tool_call in this exercise doesn't touch a real filesystem, so that exact bug can't happen here — but explain, in 2-3 sentences, what the equivalent safety check would need to look like if FAKE_DISK were swapped for a real directory on disk, and where in your dispatch logic you'd add it. Use Chapter 3's "is it consistent with the rest of the codebase's patterns" question explicitly in your answer.
