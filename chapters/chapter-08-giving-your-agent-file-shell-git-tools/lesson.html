Giving Your Agent File/Shell/Git Tools

Chapter 7 built the loop and kept the toolset to exactly three tools on purpose — enough to prove the mechanism worked, not so many that the tool layer itself became the subject. Here's a task that would break Chapter 7's agent in an unsatisfying way: "In config.py, change the timeout value from 30 to 60 — don't touch anything else in the file." With only read_file and write_file, the model's only option is to read the whole file, produce the whole file back with one number changed, and call write_file with the entire new contents. That works — right up until the file is 400 lines long and the model's reproduction of the other 399 subtly drops a comment, reformats a docstring, or (worse, and directly observed in real small-model behavior) truncates a section it decided wasn't relevant to restate. Nothing in Chapter 7's tools makes that failure visible until a human — or a later tool call — notices the file changed more than it should have.

That's not a hypothetical edge case; it's the direct, predictable consequence of only having one way to change a file: overwrite the whole thing. This chapter builds a second way — a targeted edit tool — plus a way for the agent to look before it writes (list_directory), a way to check its own work after it writes (git_status, git_diff), and an honest, partial answer to the much harder question Chapter 7's run_shell_command left completely open: what happens when a coding agent can run any shell command at all.

A Safer Edit Tool: Overwrite vs. Targeted Edit

Chapter 7's write_file has exactly one behavior: replace the entire file. That's simple to implement, simple to reason about, and genuinely the right tool for a brand-new file or a full rewrite. It's also a blunt instrument for the far more common case — the agent needs to change three lines of a file it didn't write and doesn't need to fully reproduce. Two real risks follow directly from that: the model's reproduction of the "unchanged" parts can be wrong (Chapter 5's premature-done and going-off-the-rails failure modes generalize here — confident output isn't necessarily correct output), and even when it's right, a diff that touches an entire file makes Chapter 3's review job — "does this diff only touch what it needs to touch?" — much harder than it should be for a three-line change.

The alternative this chapter builds is a find-and-replace style edit_file tool: it takes an exact string to find and a string to replace it with, and it does exactly one thing — replace that one occurrence — instead of asking the model to restate anything it isn't actually changing.

edit_file -- a targeted alternative to write_file 
def edit_file(path, find, replace):
    full = _safe_path(path)
    try:
        with open(full) as f:
            content = f.read()
    except FileNotFoundError:
        return f"error: no such file: {path}"

    count = content.count(find)
    if count == 0:
        return f"error: text not found in {path}: {find!r}"
    if count > 1:
        return (
            f"error: text {find!r} appears {count} times in {path} -- "
            "edit_file only replaces an exact, unambiguous match; include "
            "more surrounding context to make it unique"
        )

    new_content = content.replace(find, replace, 1)
    with open(full, "w") as f:
        f.write(new_content)
    return f"replaced 1 occurrence in {path} ({len(new_content)} bytes now)"

Notice what the count > 1 branch does: it refuses to guess. If find matches more than once, a real possibility for a short string like "return None" in a longer file, silently replacing "the first one" or "all of them" is exactly the kind of quiet, wrong behavior Chapter 3's review checklist exists to catch — so this tool doesn't produce that behavior in the first place. It fails loudly, with a message the model can act on next turn (ask for more context to make the match unique), the same self-correcting dynamic Chapter 4 described for any other tool result.

What is... the real trade-off here, honestly stated? write_file is simple: one code path, one thing that can go wrong (the model's reproduction is wrong), and it's the only option that works for a file that doesn't exist yet. edit_file is safer against the "wiped unrelated content" failure specifically, but it isn't free: it requires more careful schema design (what happens on zero matches? on multiple matches? Chapter 8's version above picks "fail loudly" for both), and it gives a small model more ways to be subtly wrong — a find string with a stray whitespace difference, a copy-paste that's almost-but-not-quite what's in the file, produces a clean, unambiguous "text not found" error rather than a crash, but it's still a new failure surface write_file didn't have. Neither tool is strictly better; a well-equipped agent has both and the system prompt says when to prefer which (this chapter's reference agent's system prompt does exactly that — see the assembled file below).

list_directory: Letting the Agent See Before It Guesses

Chapter 7's agent has no way to discover what files exist — it can only read a path it (or the human) already knows. That's fine for a task like "write hello.txt," where the target path is given outright. It falls apart for a task like "find the config file and update the timeout," where the agent has to guess a filename before it can call read_file at all — and Chapter 4 already established what a model does when a task under-specifies something it needs: it fills the gap with a guess, sometimes a wrong one.

list_directory -- discovery before action 
def list_directory(path):
    full = _safe_path(path)
    if not os.path.exists(full):
        return f"error: no such directory: {path}"
    if not os.path.isdir(full):
        return f"error: not a directory: {path}"
    return json.dumps(sorted(os.listdir(full)))

This is a deliberate rebuild, done correctly, of a tool Chapter 7 already showed you going wrong: project/solution.py's AI-paired list_files tool skipped _safe_path() entirely (a real boundary escape) and let a missing directory's exception fall straight through to dispatch_tool_call's generic handler instead of returning a clean, file-consistent error string. This version fixes both: every path goes through _safe_path() like every other tool in this chapter, and it distinguishes "doesn't exist" from "exists but isn't a directory" with two separate, specific error messages — because a model that gets back "error: not a directory: notes.txt" has a real chance to recover (try read_file instead), while a generic Python traceback string does not.

The tool's description matters just as much as its code here — Chapter 4's core point about tool descriptions applies directly. "List a directory's contents" (the literal wording Chapter 7's flawed AI-paired version used) doesn't distinguish itself from read_file's "read a text file" clearly enough for a small model to reliably tell them apart on an ambiguous request. This chapter's version is explicit: "List the names of files and subdirectories directly inside a directory (not a file)..." — naming the type distinction directly, because the failure it's preventing (the model calling list_directory on a file path, or read_file on a directory path) is a real, observed class of tool-selection confusion, not a theoretical one.

Git as a Tool: git_status, git_diff, and the git_commit Question

An agent that can write and edit files but has no way to see what it actually changed is flying blind in a specific, avoidable way: it has to trust its own memory of what it wrote instead of checking. Git already tracks exactly this, so wrapping two read-only git commands as tools gives the agent (and you, reading the transcript afterward) a ground-truth check that doesn't depend on the model's own narration being accurate:

two read-only git tools -- safe by construction 
def git_status():
    result = subprocess.run(
        ["git", "status", "--porcelain"], cwd=WORKSPACE,
        capture_output=True, text=True, timeout=15
    )
    if result.returncode != 0:
        return f"error: git status failed: {result.stderr.strip()}"
    return result.stdout or "(clean -- no changes)"

def git_diff(path=None):
    cmd = ["git", "diff"]
    if path:
        cmd += ["--", path]
    result = subprocess.run(cmd, cwd=WORKSPACE, capture_output=True, text=True, timeout=15)
    if result.returncode != 0:
        return f"error: git diff failed: {result.stderr.strip()}"
    return result.stdout or "(no changes)"

Look closely at how these two are built, because it's different from every tool so far: they use subprocess.run with a real Python list of arguments (["git", "status", "--porcelain"]), not a shell string with shell=True. That's not a style choice — a list of arguments is never interpreted by a shell, so there's no shell metacharacter (;, &&, backticks) for anything to inject in the first place. These two tools are read-only (they change nothing) and structurally safer by how they're called, which is exactly why they're the easy, low-risk half of "git integration as a tool."

The hard half is the question this section deliberately does not resolve: should an agent be able to call git_commit at all?

What is... the actual risk with a write-capable git tool? It's tempting to think a commit is low-risk because git revert exists — nothing is "truly" destroyed the way an unrecoverable rm -rf is. But a commit made autonomously, with a message the model itself wrote, skips the one checkpoint this entire course has built toward since Chapter 3: a human reading the diff before it becomes part of the project's real history. A plausible-looking commit message doesn't guarantee a correct diff underneath it — the same gap between "looks right" and "is right" Chapter 3 opened with. Once it's committed, it's discoverable by every other tool, every teammate, and (if pushed) every CI run downstream, whether or not anyone reviewed it first.

Here's a sketch of what a write-capable version might look like — shown for the design discussion, deliberately not wired into this chapter's reference agent's TOOLS list or TOOL_FUNCTIONS:

NOT part of this chapter's reference agent -- discussion only 
# A guarded sketch, not shipped code: even something like this still
# leaves the real decision (should the agent be allowed to commit at
# all, ever, unsupervised) unanswered -- that's Chapter 11's job.
def git_commit(message, confirm=False):
    if not confirm:
        return (
            "error: git_commit requires confirm=true -- this chapter's "
            "agent does not set that automatically for any task"
        )
    # ... subprocess.run(["git", "commit", "-m", message], ...) would go here

Notice that even a confirm flag doesn't actually solve anything by itself — nothing stops a model from simply passing confirm=true on its own, the same way nothing in Chapter 7 stopped a model from asking for a path outside the workspace; _safe_path() had to be a harness-enforced check, not a request. A real answer needs something the model can't set for itself: a human-in-the-loop confirmation step outside the model's own turn, a permission scope decided before the agent runs at all, or simply leaving commit/push out of the toolset entirely and having a human run those commands after reviewing the diff the agent produced. This is precisely Module 5's subject (Chapter 11: sandboxing, permissions, destructive commands) — this chapter names the question honestly and leaves it there on purpose, the same way Chapter 7's _safe_path section previewed Module 5 without fully covering it.

Hardening run_shell_command, Honestly

Chapter 7's run_shell_command runs literally anything, via subprocess.run(command, shell=True, ...). That's not a bug in Chapter 7 — it was named there as a deliberately minimal starting point — but it deserves to be named as what it actually is: arbitrary command execution, gated by nothing except whatever the model happens to decide to run. A 15-second timeout (already present in Chapter 7) stops a hang; it does nothing at all to stop a command that completes in under a second and deletes something.

This chapter adds one concrete, honest mitigation: a denylist — a small, named set of patterns for commands that are almost never what a coding-task agent should be running unsupervised, checked before anything runs.

a denylist, checked before execution 
SHELL_DENYLIST = [
    (r"rm\s+-rf\s+/(\s|$)", "recursive delete of the filesystem root"),
    (r"rm\s+-rf\s+~", "recursive delete of the home directory"),
    (r"\bsudo\b", "privilege escalation"),
    (r"git\s+push\b.*--force", "force-push (can destroy remote history)"),
    (r">\s*/dev/sd[a-z]", "writing directly to a raw disk device"),
    (r":\(\)\s*\{\s*:\|:", "fork bomb"),
    (r"\bmkfs\b", "filesystem-formatting command"),
    (r"\bshutdown\b|\breboot\b", "shutting down or rebooting the host"),
]

def _blocked_reason(command):
    for pattern, reason in SHELL_DENYLIST:
        if re.search(pattern, command):
            return reason
    return None

def run_shell_command(command):
    reason = _blocked_reason(command)
    if reason:
        return f"error: command blocked ({reason}): {command!r}"
    result = subprocess.run(
        command, shell=True, cwd=WORKSPACE, capture_output=True, text=True, timeout=15
    )
    return json.dumps({"stdout": result.stdout, "stderr": result.stderr, "exit_code": result.returncode})

Read the blocked reason back to the model the same way every other tool result gets read back — that's Chapter 4's mechanism again, not a special case. A rejected command becomes one more observation the model reads on its next turn, the same as a successful one.

What is... the denylist-vs-allowlist trade-off, stated without overselling either? A denylist (block a named list of dangerous patterns, allow everything else) is what this chapter ships, because it stays out of the way for the huge majority of legitimate coding tasks — running tests, listing files, checking versions — without the agent's designer having to predict every command a real task might need in advance. Its honest weakness: it can only block what someone thought to write a pattern for. rm -rf / is blocked; rm -rf $HOME/../, a base64-encoded command piped to sh, or a perfectly ordinary-looking command that happens to be destructive in this specific repository's context (like git clean -fdx in a workspace with untracked work someone actually wanted) sail straight through. An allowlist (permit only a named list of known-safe commands, block everything else by default) inverts that trade-off: genuinely safer by construction, because the default is deny, not allow — but it's also far more restrictive, and a real coding task (running an unfamiliar project's build tool, a linter with a name the allowlist author never anticipated) will get blocked constantly unless someone maintains the list actively. Neither one is "solved" security; both are mitigations a minimal agent can actually apply without becoming a full sandboxing solution. Real isolation — a container, a VM, a filesystem genuinely inaccessible outside the workspace regardless of what command runs inside it — is Chapter 11's subject, not this chapter's.

One more thing worth being honest about: this denylist runs on the exact string the model produced, matched with regular expressions. A sufficiently motivated adversarial input (this chapter isn't claiming that's the primary threat model for a coding agent you're directing yourself, but it's a real category worth naming) can construct a command that means the same thing but doesn't match any pattern — string concatenation, variable indirection, an alias defined earlier in the same command. The mitigations in this section reduce the chance an off-course or confused model call does something destructive by accident; they are not a claim that no command could ever slip through. Treating a denylist as "solved" instead of "meaningfully reduced risk" is exactly the kind of overselling this chapter is trying not to do.

The Extended Dispatch Table, Assembled

Every new tool above plugs into TOOL_FUNCTIONS and TOOLS exactly the way Chapter 7 predicted — nothing about dispatch_tool_call or run_agent changes at all:

TOOL_FUNCTIONS -- the only thing that grew 
TOOL_FUNCTIONS = {
    "read_file": read_file,
    "write_file": write_file,
    "edit_file": edit_file,
    "run_shell_command": run_shell_command,
    "git_status": git_status,
    "git_diff": git_diff,
}

# dispatch_tool_call is copy-pasted from Chapter 7, unchanged:
def dispatch_tool_call(tc):
    name = tc.function.name
    try:
        args = json.loads(tc.function.arguments)
    except json.JSONDecodeError:
        return f"error: invalid JSON arguments: {tc.function.arguments!r}"
    if name not in TOOL_FUNCTIONS:
        return f"error: unknown tool: {name}"
    try:
        return TOOL_FUNCTIONS[name](**args)
    except KeyError as e:
        return f"error: missing required argument {e} for {name}"
    except Exception as e:
        return f"error: tool {name} failed: {e}"

The full, real, runnable file — every tool from this chapter plus Chapter 7's unchanged loop — is project/starter.py. It's also the L2 project's scaffold: it's missing exactly one tool on purpose, marked with # TODO, for you to add yourself following this chapter's pattern. See the project page for the full task.

A note on verification, in the same spirit of honesty Chapter 7's reliability section modeled: every tool function above was tested directly in this chapter's build — write/read/edit round-trips, the ambiguous-match refusal, the missing-directory and wrong-type cases for list_directory, the denylist blocking real dangerous strings while letting an ordinary ls through, and _safe_path correctly rejecting a workspace-escaping path — but not by running the full agent loop against a live model this session; a local generation hang made that impossible here (the same sandbox-wide issue disclosed in this chapter's own quality audit). The tool logic itself doesn't depend on the model being reachable to verify, which is exactly the point Chapter 7's exercises made about testing dispatch logic independent of a live model — this chapter leans on that same discipline for its own new tools.

GenAI Builder Thought Process

Problem: a developer extending Chapter 7's agent reaches for "add more tools" as the obvious next step and starts writing write_file-shaped functions for everything — editing, listing, git operations — without questioning whether "overwrite the whole thing" is even the right shape for the new capability.

Assumption being made: that a tool's safety is mostly about whether _safe_path() gets called, and that the tool's behavior (overwrite vs. targeted, read vs. write, what happens on an ambiguous or missing input) is a secondary implementation detail.

What actually distinguishes it: this chapter's tools that turned out safest by construction — git_status, git_diff — are safe specifically because they're read-only; nothing about their design has to defend against a bad write, because there is no write. The tools that needed real design care — edit_file's ambiguous-match refusal, run_shell_command's denylist — needed it because they can change state, and "change state" is where a small model's occasional bad call actually costs something. The question worth asking before adding any new tool isn't just "does it use _safe_path()," it's "what's the worst thing this tool does if the model calls it with a slightly wrong argument, and does the tool's own code make that worst case loud and recoverable, or silent and permanent?"

Why this matters before Chapter 9: Chapter 9 swaps some of these hand-rolled tools for MCP-based ones — a different mechanism for exposing a tool to the model, but the same underlying questions (what does this tool actually do on a bad call, who's responsible for scoping it) don't go away just because the tool now lives behind a protocol instead of a local Python function. The habit of asking "what's the worst case, and is it loud or silent" travels with you.

Working definition to carry forward: a tool layer isn't safe because every function happens to call _safe_path() — it's safe because someone thought through each tool's worst-case bad call and made the failure loud, recoverable, and scoped, the same discipline whether the tool reads a file, edits one, runs a shell command, or reaches into git history.

Points To Remember

  • edit_file is a targeted, find-and-replace alternative to write_file: safer against silently losing unrelated content, but it requires careful schema design (what happens on zero or multiple matches — this chapter's version fails loudly on both instead of guessing) and gives a small model a new, different way to be subtly wrong. Neither tool is strictly better than the other.
  • list_directory lets the agent discover what exists before guessing a path — rebuilt correctly here from Chapter 7's own AI-paired list_files, which skipped _safe_path() and had an inconsistent error pattern; this version fixes both and gives the model two distinct, actionable error messages instead of one generic exception.
  • git_status and git_diff are read-only and structurally safer by how they're called — a Python list of arguments to subprocess.run, never interpreted by a shell, so there's no shell metacharacter for anything to inject.
  • Whether to expose a write-capable git tool (git_commit) at all is a genuinely hard, unresolved question, not a coding problem — a confirm flag alone doesn't solve it, because nothing stops a model from setting it itself; a real answer needs a check the model can't make for itself, which is Chapter 11's subject.
  • Chapter 7's run_shell_command ran literally anything; this chapter adds a named denylist of destructive patterns as a real, honest, partial mitigation — not a claim of solved security. Denylists stay usable but can only block what someone thought to write a pattern for; allowlists are safer by default-deny construction but far more restrictive. Real isolation (containers, VMs, filesystem-level confinement regardless of the command run) is Chapter 11's job, not a minimal agent's.
  • None of this changed Chapter 7's loop or dispatch_tool_call's shape at all — every addition above is a new TOOLS schema entry and a new TOOL_FUNCTIONS entry, exactly the separation Chapter 7's own closing thought-process section predicted.
