Part A — Multiple Choice

Choose the single best answer for each.

A1. What is a "tool call," mechanically, per Chapter 4?

  • (a) A separate reasoning module the model invokes outside of ordinary text generation
  • (b) A structured piece of model output — a tool name plus a JSON object of arguments — produced the same way any text is produced: as the most probable continuation of everything currently in the model's input
  • (c) A hardcoded if/else router that matches keywords in the user's request to a specific function
  • (d) A persistent background process the model stays aware of while it runs

A2. Which of the following is not one of the loop-termination mechanisms Chapter 4 actually names?

  • (a) A clean stop — a turn with no tool call
  • (b) A hard stop — a harness-enforced step/turn cap
  • (c) A confidence-threshold stop — the model halts once its internal certainty score drops below a fixed value
  • (d) A boundary stop — an explicit rule blocking or redirecting a tool call

A3. An agent tries four slightly different fixes for the same import error across four turns, with the fourth attempt nearly identical to its first. Per Chapter 5, this pattern is best described as:

  • (a) Stalling
  • (b) Looping / thrashing
  • (c) Premature "done"
  • (d) Going off the rails

A4. Per Chapter 6, when an instruction given early in a long session appears to be "ignored" 65 turns later — even though the conversation was nowhere near the model's actual token limit — what actually happened to that instruction?

  • (a) It was silently deleted from the conversation to make room for newer content
  • (b) It is still technically present, but it lost influence relative to a much larger volume of newer, unrelated material — crowding and dilution, not deletion
  • (c) The harness automatically expires instructions after a fixed number of turns
  • (d) It was moved to a separate long-term memory store the model didn't check

Part C (Failure-Diagnosis Exercise) — diagnosis key:

  • C1 is looping/thrashing. Turn 8's edit reverts to essentially turn 4's fix (int(count)), after turn 6's detour — a rotation through variants of the same idea rather than a narrowing toward new information. None of the three attempts ever addressed the actual signal in the error message (count itself is None, not merely the wrong type) — nothing in the transcript ever supplied that as a new, distinguishing fact, so each retry stayed inside the same "which cast/guard is right" space.
  • C2 is premature "done." The only test run visible in the transcript (turn 6) happened before turns 7–9's edits, including the offset-calculation change in turn 9 — exactly the kind of edit most likely to reintroduce or shift an off-by-one bug. Turn 10's "this should satisfy the acceptance criterion" is a prediction about what the code probably does, not a report of a check that was actually run after the last edit.
  • C3 is going off the rails (a compounding mistake). Turn 3's claim that apply_surcharge_v2 is "the version actually wired into the checkout flow" was never verified against anything — it was inferred from the function being newer-looking, not from reading anything that actually traced checkout's call path. Every turn after that treats it as settled, and turn 5 edits the tests to match the assumed function rather than checking which one checkout truly calls. Turn 7's "the checkout function checkout actually uses" restates the original guess with more confidence than turn 3 ever had, and the test suite passing proves nothing about which function is real, since the tests were edited to match the assumption in turn 5.
