Chapter 12 Exercises ~45 min

Exercises: Putting an Agent in CI

These exercises don't need Ollama, a live model, network access, or even a real git repo to verify — starter.py and solution.py in this folder rebuild the CI policy layer's own building blocks (a scratch-scope check, a protected-branch check, and the mode-aware fail-closed policy lookup) as small, testable functions.

Exercise standard Six tasks below. At least three are production-gear: harder, ambiguous, real-world judgment calls rather than clean textbook cases.

1 Implement in_scratch

Open starter.py. Fill in TODO 1: a scratch-prefix check, careful to strip only a literal leading "./" rather than using str.lstrip() (which would silently mangle a real path escape like "../../etc/passwd"). Run python3 starter.py and get the first seven checks to PASS.

2 Implement is_protected_branch

Fill in TODO 2: a protected-branch check that treats an UNDETERMINED branch (None) as protected, not as "probably fine." Get the next four checks to PASS.

3 Implement resolve_tier

Fill in TODO 3: the mode-aware, fail-closed policy lookup that stands in for active_policy() + check_permission() combined. Get the remaining six checks to PASS.

4 (Production-gear) Design a tier and scope for a genuinely new CI tool

Your team wants to add a deploy_to_staging(version) tool to a CI troubleshooting agent built on this chapter's code. It deploys a build to a real, shared staging environment other engineers actively use for testing — not a disposable scratch resource. Should it appear in TOOL_POLICY_CI at all? If so, at which tier, and does it need a code-level scope check the way write_file and git_commit do — or is this exactly the kind of tool this chapter's design says has "no narrow scope that makes it safe unattended," the same category run_shell_command falls into? Write 3-4 sentences defending your answer.

5 (Production-gear) Trace a real environment-variable footgun

A teammate writes a GitHub Actions workflow with env: ACAFE_CI_MODE: true (no quotes) instead of env: ACAFE_CI_MODE: "1". GitHub Actions coerces every env: value to a string before the process sees it, so the agent's own process receives the literal string "true" as os.environ["ACAFE_CI_MODE"]. Using project/solution.py's actual line (CI_MODE = os.environ.get("ACAFE_CI_MODE") == "1"), trace exactly what CI_MODE evaluates to, which policy dict the run actually uses, and what the OBSERVABLE symptom would be (does the agent do something dangerous, or does it just... not do anything useful?). What does your answer reveal about why this chapter's fail-closed defaults matter even when the bug is in the CI-mode DETECTION itself, not in the policy dicts?

6 (Production-gear) Review a PR that updates one policy but not the other

A diff adds a new tool, run_linter(), to TOOLS and TOOL_FUNCTIONS, and adds an entry for it to TOOL_POLICY (ALLOWED — it's read-only) — but the PR author forgot to add a matching entry to TOOL_POLICY_CI. Using active_policy()'s actual behavior (not a guess), what happens the first time this tool is called during a CI run versus an interactive run? Is this a bug worth blocking the PR over, or is the two-dict, fail-closed-per-dict design already handling it safely? Write 3-4 sentences with reference to the actual code path in check_permission()/active_policy().
