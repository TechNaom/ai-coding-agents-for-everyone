Level 1 Project: Ship a Real Small Feature With a Coding Agent

This is it — the project Chapters 1 and 2 both pointed to as "unlocks after Chapter 3." You now have all three pieces this module teaches: the loop/autonomy mental model (Chapter 1), how to scope a task so an agent can actually succeed at it (Chapter 2), and how to review what it hands back like a senior engineer would (this chapter). This project asks you to use all three, for real, on a real (small) codebase, and to produce a written artifact that proves you did.

The deliverable has two halves, and both are graded by the same standard a senior engineer would actually use: a working diff, and an honest review log that shows your reasoning — not just your verdict. A perfect diff with no review log doesn't demonstrate the skill this module teaches; neither does a review log for a feature that doesn't actually work. You need both.

What you'll need

  • Any coding agent tool you have access to — Claude Code, Cursor's agent mode, GitHub Copilot's agent mode, or an equivalent. This course is intentionally tool-agnostic (per docs/course-architecture.md): the judgment matters more than the specific product, and none of it is Claude Agent SDK code — that starts in Module 3.
  • A small, real codebase you're allowed to modify: your own side project, a personal repo, a small open-source project you already contribute to, or a fresh throwaway repo you scaffold yourself with a handful of files and at least a minimal way to check behavior (a test suite, or a script you can run and inspect). It does not need to be large or impressive — a codebase you can hold in your head is actually the right size for this project.
  • A way to save two artifacts: the agent's diff (a patch file, a screenshot of the tool's diff view, or a link to a local commit), and your written review log (plain Markdown or text is fine).

Step 1 — Pick one small, real feature or fix

Choose a task sized like the well-scoped examples from Chapters 1 and 2 — not a one-line rename (too small to be worth an agent's overhead), not "modernize the module" (open-ended, no natural stopping point). Pick something you'd genuinely be glad to have built. A few shapes that fit the right size, pick one or invent your own of similar scope:

  • Add a field with validation — a new optional field on an existing form, API endpoint, or data model, with input validation and a test covering the invalid case.
  • Fix a specific, reproducible bug — something with a clear repro steps and a test you can point the agent at, the way Chapter 2's cache-key example worked.
  • Add a small, self-contained capability — CSV export of an existing report, a rate limit on one endpoint, a confirmation step before a destructive action, pagination on an endpoint that currently returns everything at once.
  • Add a guardrail — input sanitization, a permission check that's missing on one route, an idle-session timeout — something with real, checkable behavior before and after.

If you don't already have a codebase with something like this waiting, the fastest path is a small personal utility: a script or tiny web service you build in twenty minutes (even a to-do list API or a CLI tool), specifically so you have a codebase small enough to fully understand yourself — which matters for Step 3, review.

Step 2 — Write a scoped prompt (Chapter 2)

Before you open the agent, write the prompt out first, as its own artifact, using Chapter 2's three ingredients:

prompt checklist 
1. Context: the specific symptom or goal, and which file(s)
   or area of the codebase it lives in.
2. Scope boundary: what's explicitly in play, and what the
   agent should stop and ask about before touching.
3. Acceptance criterion: a condition you (and the agent) can
   check mechanically -- a test passing, a specific behavior
   verified by running the code -- not a subjective goal.

Save this prompt exactly as you send it to the agent. It becomes the first section of your review log, and it's also the yardstick the rest of the review measures against — you can't check whether a diff matches its acceptance criterion if you didn't write one down.

Step 3 — Run it, then review it like Chapter 3, not like a rubber stamp

Let the agent run its plan/act/observe loop and hand back a diff. Do not accept it on sight. Work through the five checks from the lesson, in the triage order the lesson recommends (file list and acceptance criterion first, full attention on anything unexpected or high-risk, a lighter pass on mechanical expected changes):

  1. Does the diff actually satisfy the acceptance criterion, or just pass a check on a technicality?
  2. Did it touch any file outside what the prompt named as in scope?
  3. Is there any change you can't justify in one sentence?
  4. Does it introduce a pattern inconsistent with how the rest of your codebase already does similar things?
  5. Could this be a fix for the symptom rather than the root cause — would a slightly different input bring the same problem back?

If the diff fails any of these, don't just fix it yourself — go back to the agent with a specific follow-up (exactly as you'd do with a human teammate's PR) and record what you asked for and what came back. A review log that shows one round of "found a problem, asked for a fix, verified the fix" is a stronger submission than one where the agent happened to get it right the first time — it's direct evidence you can actually catch a real problem, not just that you got lucky.

Step 4 — Write the review log

The review log is the actual graded artifact of this project — the diff on its own doesn't prove you reviewed it well. Use this structure:

review-log.md — required sections 
# Review Log: <feature name>

## Task and prompt
<the exact prompt you sent, verbatim>

## Acceptance criterion
<copied from the prompt, stated as a checkable condition>

## Diff summary
<one line per changed file: what changed and why, in your
own words -- not copy-pasted from the agent's summary>

## Checklist results
- Matches acceptance criterion (not just passes it)? <yes/no + why>
- Stayed inside the stated boundary? <yes/no + why>
- Every change justified? <yes/no -- list anything you
  couldn't explain, and how you resolved it>
- Consistent with existing codebase patterns? <yes/no + why>
- Root-cause fix, or could this be a symptom fix?
  <your reasoning, including what input might break it again>

## Verdict
<Approved as-is / Approved after follow-up (describe the
follow-up and what changed) / Rejected and redone>

## Time
<rough time the agent took vs. rough time you spent
reviewing -- this is a real number worth tracking>

Write every section honestly, including when the answer is "yes, this passed the check cleanly." A review log that just says "everything looked fine" for each item isn't useful — the value is in the specific reasoning: why you're confident the fix is root-cause rather than symptom, why a given change is justified, not just a checkmark. If you genuinely found nothing wrong, say what you actually checked to reach that conclusion.

What "done" looks like

  • The feature works — you've personally verified the acceptance criterion yourself, not just trusted the agent's report that it passed.
  • You have a saved copy of the prompt you wrote and the diff the agent produced.
  • review-log.md (or equivalent) exists, follows the structure above, and every checklist item has real reasoning behind it — not a bare yes/no.
  • If you caught a problem during review, the log documents the follow-up round: what you asked for and what changed as a result. If you didn't catch anything, the log explains specifically what you checked to be confident in that.
  • The prompt itself holds up against Chapter 2's three ingredients — context, scope boundary, acceptance criterion — and the log briefly notes whether, in hindsight, the prompt could have been scoped better.
Where this fits Module 1 — Using Coding Agents Well: Chapter 1 built the loop/ autonomy mental model, Chapter 2 covered prompting and scoping, Chapter 3 (this chapter) covers reviewing the result. This project is the Level 1, Guided project from the course's curriculum map — the first of four projects (L1 through L4) — and it's the one place in Module 1 where all three chapters have to work together on a real, non-hypothetical change.

Why this project is structured this way

A project that only asked you to "use an agent to build something" would test whether you can operate the tool, which was never the hard part. The hard part — and the actual point of this module — is writing a request precise enough that the agent can succeed, and then not trusting the result just because it looks clean and the tests are green. The review log exists specifically because "I reviewed it" is an unfalsifiable claim and "here's what I checked and what I found" isn't. If this project only asked for the diff, it would be measuring luck as often as it measured judgment.
