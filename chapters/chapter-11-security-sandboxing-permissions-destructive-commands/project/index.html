Chapter 11 Project ~45 min · Module 5 Lab

Project: Add Permission Scoping to the Module 3 Agent

Per docs/curriculum/CURRICULUM_MAP.md, Module 5's lab is exactly this: "add permission scoping to the Module 3 agent." starter.py in this folder is Chapter 8's reference agent, copied forward unchanged, plus a real git_commit tool — the one Chapter 8 sketched, named the flaw in (a confirm=True argument the model can set on itself is not a real permission check), and shipped nowhere. Your job is the missing piece: a permission-scope layer that lives entirely in the harness, checked before any tool call is dispatched, that a model cannot see, set, or talk its way around.

What's provided

Every tool from Chapter 8 (read_file, write_file, edit_file, list_directory, a denylist-and-resource-limit-hardened run_shell_command, git_status, git_diff) plus two new tools: a real git_commit (finally resolving Chapter 8's open question) and a send_email stub included purely to give this project a concrete example of the strictest policy tier. None of the tool functions themselves are TODOs — they're tested, working scaffold, the same role Chapter 8's five tools played for that chapter's project.

Your task

Four TODOs in starter.py, all part of one connected mechanism: define the three policy tiers (ALLOWED/REQUIRES_CONFIRMATION/BLOCKED), build TOOL_POLICY classifying every tool into one of them, implement check_permission() (defaulting to BLOCKED for anything unclassified) and confirm_with_human() (a real input() read from real stdin, denying by default on EOF), then wire the policy check into dispatch_tool_call so it runs before any tool function is ever called. Full spec in the module docstring and each TODO.

What "done" looks like Running python3 starter.py (or solution.py) executes a five-part scripted demo with no live model needed: an ALLOWED tool (read_file) runs instantly; a REQUIRES_CONFIRMATION tool (write_file) pauses for a real stdin prompt and denies cleanly when no human answers; a BLOCKED tool (send_email) is refused before any prompt at all; a registered-but-unclassified tool is refused too, proving the fail-closed default; and a genuinely unknown tool name is rejected as it always was. None of this requires Ollama to be running — the permission layer is pure harness logic, verifiable on its own, exactly like Chapter 7's exercises taught for tool-dispatch logic generally.

Why this is the right project for right now

Every chapter since 7 has been building toward a moment where the harness has to make a decision the model cannot override. Chapter 7's _safe_path() did it for file paths. Chapter 8's denylist did it for the worst shell commands. Both were real, but both were narrow — a boundary and a blocklist, not a general answer to "should this specific action, right now, actually be allowed to happen." This project builds that general answer: a policy the harness owns completely, checked before dispatch, with a genuine human-in-the-loop pause for anything that changes state. It is the direct, concrete resolution of the question Chapter 8 spent an entire section naming and refusing to fake an answer to.

Before you call it done

Run python3 starter.py < /dev/null — with stdin closed, does every REQUIRES_CONFIRMATION call deny cleanly instead of hanging? That single test is the most important one in this project: a permission system that hangs or silently defaults to yes when nobody's there to answer isn't safer than having no permission system at all, in the specific case that actually matters most (an agent running unattended).
