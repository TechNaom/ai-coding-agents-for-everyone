Chapter 10 Project ~40 min · Module 4 Lab

Project: Review a Deliberately-Flawed AI-Generated PR

Per docs/curriculum/CURRICULUM_MAP.md, Module 4's lab is "a deliberately-flawed AI-generated PR to review and fix." Since Module 4 is a single chapter carrying the whole module, this project is built to match: a real, three-file PR (flawed_pr/aggregate.py, flawed_pr/export_csv.py, flawed_pr/notify.py) implementing a plausible small feature — a weekly sales report, exported to CSV and emailed to a distribution list — with five deliberate flaws planted across it, plus one line that's deliberately fine. Read README.md first for the full story, including exactly what the agent claimed it tested before handing this PR over.

What's provided

The three files linked above are the PR itself, as delivered — short, plausible-looking, and not obviously broken on a quick read. starter.py is a review harness with four functions left as TODOs — the same mechanical checks this chapter's lesson and exercises taught, built into a runnable script against the real files instead of small fakes.

Your task

Two parts, in this order:

1. Review by hand first. Read all three files in flawed_pr/. For every call you're not 100% sure is real, check it — hasattr(), dir(), or an actual real call, not memory. For every function with a boundary, a default argument, or a condition, trace a concrete case. Write down what you find, and for each item: is it a hallucinated API or a logical bug, and which of Chapter 3's five review questions would catch it.

2. Then fill in and run the harness. Implement method_exists, try_run, trace_week_boundary, and trace_mutable_default_leak in starter.py (full spec in each function's docstring), then run it against the real flawed_pr/ files. Compare what it surfaces against your own by-hand review from step 1.

What "done" looks like Your review (by hand and via the harness together) should identify 5 real flaws — 3 hallucinated API calls (one a wrong method name that always crashes, one a wrong assumption about a method's return value that always crashes, one a wrong module-function name that only crashes on a code path the agent's own smoke test never reached) and 2 logical bugs (an off-by-one boundary that contradicts its own docstring, and a mutable-default-argument leak that a single-call smoke test structurally cannot see) — plus 1 line that resembles Chapter 3's rounding-bug hook but is actually fine, to test whether you over-flag on pattern-match alone. solution.py is the harness fully filled in; review_answer_key.md is the complete, file-by-file explanation of every item, including why a quick read tends to miss each one — read it only after your own pass.

Why this is the right project for right now

Every prior module in this course ended with something you built. This one ends with something you catch. Module 3 gave you a working agent; this project hands you exactly the kind of output that agent — or any agent — can produce: clean-looking, well-formatted, individually plausible code that is nonetheless wrong in five separate, specific, catchable ways. The skill Module 4 is teaching isn't "read more carefully" — it's knowing which two mechanical checks (does the call actually exist, does the logic actually do what its own contract claims) to run, and running them, instead of trusting how confident and tidy a diff looks.
