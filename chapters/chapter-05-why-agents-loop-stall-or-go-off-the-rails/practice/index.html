Chapter 5 Practice Bank ~18 min

Practice Bank: Why Agents Loop, Stall, or Go Off the Rails

Short scenarios, one judgment question each — practice spotting these four failure modes in situations where the transcript looks fine at first glance.

Scenario · "It's just being thorough"

The fifth read of the same file

A teammate reviewing a long transcript says: "It's fine, it's just being extra careful — it re-read the config file a few times." You check: the file's contents haven't changed since the first read, and none of the three later reads were preceded by anything else new entering context. Explain why "being careful" isn't the right description here, and name the failure mode along with the one piece of evidence (or lack of it) that settles the question.

Scenario · A guess that hardened into fact

"As established earlier..."

On turn 4, an agent writes: "As established earlier, the User model's email field is unique at the database level." Turn 2, the only earlier turn discussing the model, actually said: "The email field is probably unique at the database level, though I haven't checked the schema migration." Explain what changed between turn 2 and turn 4's phrasing, why that change matters even though no new tool call happened in between, and what a reviewer scanning only turn 4 would miss without reading turn 2.

Scenario · The reassuring final message

"All tests pass" — do they?

An agent's last turn: "I've completed the refactor and all tests pass." The transcript's last run_tests tool call and result appear four turns earlier, before two subsequent edit_file calls that were never followed by another test run. What should a reviewer do before accepting "all tests pass," and why does the specific ordering here (edits after the last real test run) matter more than the wording of the final message?

Scenario · Retrying with more force

The instruction that didn't help

After watching an agent fail the same way twice, a developer types: "Try harder this time, make sure it actually works." The third attempt fails in the same way as the first two. Using this chapter's mechanism, explain why "try harder" is unlikely to change the outcome on its own, and propose what the developer should have supplied instead to actually break the pattern.

Scenario · A boundary that would have helped

The wrong file, confidently edited

An agent tasked with "fix the pricing bug in the checkout service" ends up editing legacy/pricing_v1.py — a file the production service hasn't imported in over a year — because an early, unverified guess about which pricing module was "the" pricing module was never challenged. If the task prompt had included an explicit boundary like "confirm the active pricing module with me before editing any file matching pricing*," would that have prevented the wrong guess, or only limited its damage? Explain the distinction using this chapter's terms.

Scenario · Reading a stall from the outside

The dashboard shows "in progress" for forty minutes

A CI dashboard shows an unattended agent run still "in progress" well past the time similar tasks usually take. You don't have live access to the transcript yet, only the step count, which is increasing steadily. What two things would you want to check first once you do get transcript access, to tell a genuinely slow-but- productive run apart from a stall, and why would step count alone not answer that question?
