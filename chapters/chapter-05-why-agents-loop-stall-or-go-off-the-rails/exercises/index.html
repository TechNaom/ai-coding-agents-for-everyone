Chapter 5 Exercises ~30 min

Exercises: Why Agents Loop, Stall, or Go Off the Rails

Still conceptual — no SDK or code execution here, that starts in Module 3. Each exercise hands you a transcript excerpt. The work is identifying, precisely, which named failure mode is happening and what specific mechanism produced it — not just labeling it "the agent messed up."

Exercise standard Six tasks below. At least three are production-gear: harder, ambiguous, real-world judgment calls rather than clean textbook cases.

1 Name the failure mode

Four transcript fragments, each showing only the last few turns:

  1. Turns 6, 7, and 8 each call run_shell("npm test") with no edits between them, and the output is identical each time.
  2. Turn 4 calls edit_file with a one-character typo fix; turn 6 calls edit_file reverting that exact change; turn 8 calls edit_file reapplying it.
  3. The final turn is text only: "Migration complete, all records now use the new schema" — with no tool call showing the migration script was actually executed anywhere in the visible transcript.
  4. Turn 2 says "the config is loaded from settings.yaml"; turn 5 says "since we've confirmed config comes from settings.yaml, I'll add the new key there," though turn 2 never actually opened or searched for the config-loading code — it was an assumption stated as if verified.

For each, name which of the four failure modes from the lesson it is, and point to the specific detail that identifies it (not just "it seems wrong").

2 Thrashing or genuine iteration?

Two transcripts, both showing three failed attempts to fix a bug before a fourth succeeds:

Transcript A: attempt 1 fails with "AttributeError: NoneType." Attempt 2 (a different fix) fails with the identical error. Attempt 3 (yet another variant) fails with the identical error again. Attempt 4 finally succeeds after using the identical approach as attempt 1, unchanged.

Transcript B: attempt 1 fails with "AttributeError: NoneType on line 40." The agent reads the surrounding function and finds the value can come from two code paths. Attempt 2 handles path one, fails with a different error pointing at path two. Attempt 3 handles path two and succeeds.

Explain, using this chapter's distinction, why A is thrashing and B is not, even though both show three attempts before success.

3 Write the missing forcing fact

Recall the lesson's import-error hook: the agent rotated through utils.dates, a relative import, and back to the original from utils import format_date, three times, without ever checking what utils actually resolves to as a package. Write the single tool call (name and argument) that, if inserted right after the first failure, would most likely have supplied the forcing new fact needed to break the loop — and explain specifically why that fact changes what the next prediction is conditioned on, versus what the three actual retries were conditioned on instead.

4 (Production-gear) The confident diff that ships the wrong fix

A production incident ticket says: "Users report duplicate order-confirmation emails." An agent's transcript: turn 2 finds two places that could plausibly send the email — orders/notify.py:send_confirmation() and a Celery task in tasks/email_tasks.py that also references "confirmation." Turn 3: "The duplicate is coming from send_confirmation() being called twice in the checkout flow — I'll add a guard there." No tool call in turns 1-3 actually traced the checkout flow's call sites to confirm this. Turns 4-9 implement and test the guard against send_confirmation(), and the final turn declares the bug fixed. Using this chapter's account of compounding mistakes, explain exactly where the unverified premise entered, why the following six turns couldn't have caught it on their own, and what a reviewer should specifically check before merging this diff (not "review it more carefully" — name the concrete artifact to check).

5 (Production-gear) Design a stalling detector

Your team runs agents inside a harness that logs every tool call and its arguments. You want an automated check that flags a likely stall (not a certain one — a human still reviews flagged runs) without access to the model's reasoning, only the raw tool-call log. Propose a specific, concrete rule using only tool names, arguments, and results you could compute from the log (for example: "flag if the same tool is called with identical arguments twice within any 5-turn window and no edit_file or run_tests call occurs between them"). Explain why your rule wouldn't also incorrectly flag transcript B from exercise 2 above, and name one legitimate pattern your rule risks false-flagging anyway.

6 (Production-gear) The step cap that fired at the worst time

A 30-step cap fires mid-task on a database-migration agent. The last five turns before the cap: turn 26 edits the migration script, turn 27 runs it against a test database, turn 28's result shows a foreign-key constraint failure, turn 29 edits the script to add a deferred constraint, turn 30 (the cap) is a tool call to re-run the migration that never got its result because the harness cut it off first. Using this chapter's and Chapter 4's stop-condition vocabulary together: (a) name which stop condition actually ended this run, (b) argue whether the transcript shows thrashing/stalling that a higher cap would just prolong, or genuine narrowing progress that a higher cap would likely let finish, and (c) state what specific evidence in turns 26-30 supports your answer to (b).
