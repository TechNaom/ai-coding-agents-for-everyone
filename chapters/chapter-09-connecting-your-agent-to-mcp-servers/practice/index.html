Chapter 9 Practice Bank ~26 min

Practice Bank: Connecting Your Agent to MCP Servers

Module 3's assessment is a working code review checklist, not a written exam — this bank leans directly into that. A runnable script (starter.py / solution.py in this folder) hands you four small MCP-integration diffs, each with one deliberate flaw, and its own answer key referencing Chapter 3's five review questions. Predict, then run, then work through the seven scenarios below, which extend the same review discipline to situations the script doesn't cover.

Scenario · Review

The schema that looked fine in the demo

A coworker's connect_git_tools() passes every manual test they tried — the agent successfully calls git_status and git_diff in a live demo. During review, you notice the discovered tools' schemas still list workspace as a required argument the model can set. Why did the demo work anyway, and what's the realistic failure case this schema bug would actually cause in a run the demo didn't happen to exercise?

Scenario · Trade-off

The teammate who wants everything behind MCP

A teammate argues the whole team should standardize on MCP for every new agent tool going forward, "since we already have the plumbing now." Using this chapter's three criteria (agent-specific state coupling, fixed vs. arbitrary behavior, actual reuse/blast-radius), name one tool type from Chapter 8 that should stay hand-rolled even with MCP plumbing already available, and explain why "we already have the infrastructure" isn't itself a reason to use it everywhere.

Scenario · Failure mode

The server that's up but slow

mcp_git_server.py is running and reachable, but a disk issue on the machine makes every git status call take 12 seconds instead of milliseconds. MCPBridge's _call() method has a timeout parameter. What should actually happen when that timeout fires mid-task — and is "crash the whole agent" or "silently treat it as if git_status said nothing changed" ever the right default? What's the honest third option?

Scenario · The confident stakeholder pitch

"MCP means our tools are basically plug-and-play now"

A product manager, excited after reading about MCP, says "great, now any team can just plug their agent into our git tools server with zero integration work." Using what this chapter's own MCPBridge class had to solve (the sync/async bridging problem specifically), explain what's actually still real integration work for a NEW client connecting to an existing MCP server, even though the server itself needs no changes.

Scenario · Ambiguous ownership

Who reviews mcp_git_server.py?

Your team's existing review process assigns every pull request to whoever owns the affected agent. A change to mcp_git_server.py potentially affects every agent connected to it, not just the one your team happens to be working on. What does this suggest about how review ownership should differ for a shared MCP server's code versus a single agent's own hand-rolled tool, and why does Chapter 3's "did it touch anything outside the stated boundary" question need a wider definition of "boundary" here?

Scenario · The graceful-degradation trap

When "gracefully continuing" hides a real problem

connect_git_tools() returning False and letting the agent continue without git tools is the right default failure behavior, per this chapter's own reasoning. Now imagine the SAME graceful degradation happening silently on every single run for three weeks because a config typo broke GIT_SERVER_SCRIPT's path, and nobody noticed because every run still "succeeded." What's the gap between "doesn't crash" and "doesn't hide a real, ongoing problem," and what would you add to this code to close it?

Scenario · Scoping a task

The vague cleanup task, one more time

Same setup as Chapters 7 and 8's practice banks: a learner passes the task "clean up the workspace" to this chapter's MCP-extended agent. Does routing git_status/git_diff through MCP instead of a local function change how risky this vague task is, compared to Chapter 8's version — or is this one of the cases where the swap this chapter made is genuinely invisible to that particular risk? Explain your answer using the loop's actual behavior, not just intuition.
