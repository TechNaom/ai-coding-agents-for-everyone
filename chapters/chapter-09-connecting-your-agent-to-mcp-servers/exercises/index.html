Chapter 9 Exercises ~45 min

Exercises: Connecting Your Agent to MCP Servers

This chapter's exercises don't need a running MCP server, an installed mcp package, or a live model to verify — starter.py and solution.py in this folder test the schema-translation, dispatch-routing, and result-unpacking logic against small fake stand-ins, so every exercise below is checkable by running the file directly.

Exercise standard Six tasks below. At least three are production-gear: harder, ambiguous, real-world judgment calls rather than clean textbook cases.

1 Implement strip_injected_args

Open starter.py. Fill in TODO 1 inside strip_injected_args: given an MCP tool's raw schema and a set of harness-injected argument names, return a new schema with those names removed from both properties and required, without mutating the input. Run python3 starter.py and get the first five checks to PASS.

2 Implement classify_tool_call

Fill in TODO 2 inside classify_tool_call: return "local", "mcp", or "unknown" for a given tool name, checking local tools first. Get the next three checks to PASS.

3 Implement mcp_result_to_text

Fill in TODO 3 inside mcp_result_to_text: given a fake MCP result object, return the correct string dispatch_tool_call should pass back to the model — a formatted error if is_error is true, the first content block's text on success, or a stringified structured_content as a last resort. Get the remaining three checks to PASS.

4 (Production-gear) Trace a malformed schema by hand

Without running any code, work out what strip_injected_args({"type": "object"}, {"workspace"}) returns — a schema dict entirely missing both properties and required keys, not just an empty one. Write out each line of your implementation that gets triggered, in order, and what each intermediate value equals. Then run it and confirm your trace was right. This mirrors a real situation: not every MCP server's schema is guaranteed to include every JSON-Schema key, and code that assumes schema["properties"] always exists will crash on one that doesn't.

5 (Production-gear) What happens on a name collision?

Suppose a hand-rolled local tool and a discovered MCP tool happen to share the same name — say, someone later adds a local git_status function to TOOL_FUNCTIONS without realizing an MCP server already provides one. Using classify_tool_call's actual checking order (local first), trace which implementation would actually run, and explain in 2-3 sentences why silently picking one over the other — instead of raising an error or logging a warning about the collision — is a real design gap worth flagging in a code review, even though the code "works" either way. Then add a test case to a copy of starter.py that would have caught this collision if it happened.

6 (Production-gear) Review a flawed connect_git_tools() diff

A coworker submits this diff to connect_git_tools(): they changed the failure path so that if bridge.list_tools() raises an exception, the function re-raises it instead of printing a message and returning False, arguing "failing loudly is more honest than silently continuing with fewer tools." Using Chapter 3's five-question review checklist (does it match its stated goal, does it stay inside its boundary, is the change justified, is it consistent with the rest of the file, is it a root-cause fix or does it trade one problem for a worse one), write a 3-4 sentence review of this specific change. Is "more honest" actually the right frame here, given what a crash at this exact point would do to the rest of main()'s error handling?
