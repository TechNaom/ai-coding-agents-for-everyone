Detecting Hallucinated APIs and Logical Bugs

Module 3 built an agent. Everything before that taught you how to drive one well. This chapter is Module 4 on its own — the entire module, per the curriculum map — and it's about the specific, mechanical skill that sits underneath Chapter 3's five-question checklist and Chapter 5's warning about compounding mistakes: how do you actually tell, line by line, that a piece of agent-written code calls something that doesn't exist, or does something that isn't what it claims? Not "does this feel right" — a checkable, repeatable answer.

The ticket: "Sort the customer export by signup date, most recent first. Customers with no recorded signup date should sort last, not first or crash the export. Fix in reports/customers.py. Acceptance: pytest tests/reports/test_customers.py passes." A clean, well-scoped prompt by Chapter 2's standard. The agent reports success. Here's the diff.

reports/customers.py — agent's diff 
--- a/reports/customers.py
+++ b/reports/customers.py
@@
 def export_customers(df):
-    df = df.sort_values(by="signup_date", ascending=False)
+    df = df.sort_values(
+        by="signup_date", ascending=False,
+        na_position="last", ignore_na=True,
+    )
     return df.to_csv(index=False)

This reads exactly like a correct, minimal fix. na_position="last" is real — that's the actual pandas keyword for controlling where missing values sort to. ignore_na=True sits right next to it, formatted identically, explained by nothing more than its own plausible name. It does not exist. DataFrame.sort_values has no ignore_na parameter — calling it live raises TypeError: DataFrame.sort_values() got an unexpected keyword argument 'ignore_na'. Did you mean 'ignore_index'? the instant this line actually runs — pandas's own error even names the real, similarly-spelled parameter the hallucination was probably drifting toward. If the agent's own "acceptance check passed" claim was taken at face value without anyone actually running the export path the test suite happens not to cover, this ships broken and nobody notices until a customer export crashes in production.

Notice what didn't fail: the diff format. The code style. The argument name's plausibility — ignore_na sounds exactly like something a well-designed sorting function should have, and other libraries genuinely do have arguments shaped like it (Series.mean(skipna=True) is real pandas API, just not on this function). The only thing that actually catches this is running the line and watching it raise. That's the whole first half of this chapter, made concrete before any explanation of why it happens.

Hallucinated APIs: a Plausible Call That Isn't Real

A hallucinated API is a function, method, or argument that a model calls with complete syntactic confidence, formatted identically to a real call, that does not actually exist in the library or module being used. Not a typo — a typo looks broken. A hallucination looks exactly like the real thing, because it was generated the same way the real thing would have been: as plausible-sounding text.

Chapter 4 established the mechanism this chapter now applies to a specific failure: every token a model produces, including a method name inside a tool call's arguments, is the most probable continuation given everything in its context — not a lookup against a live copy of the library's actual source. A model has no built-in mechanism that checks "does ignore_na actually appear in pandas's real parameter list" before emitting it; it only has "how often, across everything this model was trained on, does text shaped like this tend to appear next to text shaped like na_position='last'." For a structurally plausible argument on a widely-used function, that probability can be high even when the argument is entirely invented — especially in three recurring situations:

Less common libraries and less-seen call shapes. A model has seen thousands of real requests.get(url, timeout=5) calls and far fewer examples of a smaller, less-documented library's exact method surface. Where training data is thin, "what's plausible" and "what's real" diverge more often, because there's less real signal pulling the prediction toward the actual API.

APIs that changed after the model's training data. A method deprecated, renamed, or removed in a newer library version can still be exactly what a model predicts, because that call shape was genuinely common in the text it learned from — the model has no way to know the library moved on since then.

Structural similarity to a more common library. This is the hook's exact mechanism. Chaining calls is common and idiomatic in libraries like pandas (df.dropna().reset_index()) and in many JavaScript APIs — so a model reaching for a stdlib call that looks like it should chain the same way can confidently produce a chain that the actual library never supports:

a chained call that assumes a fluent API that doesn't exist 
from email.message import EmailMessage

msg = EmailMessage()
msg.set_content("See attached report.").add_attachment(
    csv_bytes, maintype="text", subtype="csv", filename="report.csv"
)
# AttributeError: 'NoneType' object has no attribute 'add_attachment'
# -- EmailMessage.set_content() mutates msg in place and returns None,
# it isn't a fluent/chainable API the way this call assumes.

Every one of these is the same underlying event: a highly probable piece of text that happens not to correspond to anything real. It is not the model "lying" and it is not "making a mistake" in the way a person forgetting a detail makes a mistake — it's the mechanism from Chapter 4, applied to the one place its output has to be literally, exactly correct to work at all: a name that either exists in a library's real surface or doesn't.

What is... a hallucinated API, precisely? Any function name, method name, module attribute, class, or keyword argument that a piece of generated code references as if it exists, but that the actual library, module, or standard library being called does not define — regardless of how plausible, well-formatted, or confidently explained the call looks. The three usual shapes: a wrong-but-close name (DictWriter.write_all instead of the real writerows), a nonexistent argument on a real function (ignore_na on sort_values), or a wrong assumption about what a real call returns (assuming a mutating, None-returning method is chainable).

Catching a Hallucinated API, Mechanically

"Does this look right" is exactly the check a hallucinated API is built to survive — the whole reason it's dangerous is that it looks right. Catching one requires a check that doesn't depend on how a line of code reads. Three checks actually work, in order of cost:

1. Does the name actually appear in the library, via introspection or real documentation — not memory? This is cheap and immediate: dir(obj), hasattr(obj, "method_name"), or help(SomeClass.method) tell you, directly from the installed package on your machine, whether a name is real. This is strictly better than trusting your own memory of the library or the model's own confident explanation of it — both can be wrong in the same direction a hallucination is wrong, because both are pattern-matching against "what usually goes here," not checking the actual installed version.

a two-line introspection check, before trusting a claimed call 
>>> import csv
>>> hasattr(csv.DictWriter, "write_all")
False
>>> hasattr(csv.DictWriter, "writerows")
True

2. Does it actually import and run — the full call, with real or realistic arguments, not just the module? This is this course's own build discipline, stated plainly: PROJECT_STATE.md and every chapter's quality audit in this repository record, explicitly, that no code example was written into a lesson without first being run against the actually-installed package — Chapter 9's audit describes installing the real mcp package and inspecting its real function signatures with inspect.signature() before trusting any claim about its API, specifically because trusting memory or a plausible-looking call is exactly the failure this chapter is about. The same discipline applies to any code an agent hands you: importing a module cleanly proves the module exists, nothing more — only actually calling the specific method with real arguments proves that call is real. hasattr() catches a wrong name; running the call also catches a wrong argument, because Python raises TypeError immediately for a keyword argument a function's real signature doesn't define.

What is... the gap between "it imports" and "it runs correctly"? Importing pandas only proves the package is installed. Calling df.sort_values(...) with the exact arguments the diff uses is the only thing that proves those specific arguments are real — and it has to be the exact call, on realistic data, not a simplified stand-in, because a hallucinated argument on a rarely-exercised branch (a specific error-handling path, a specific input shape) can sit unnoticed through a shallow "does the script run at all" smoke test that never actually reaches that line. This is the same gap Chapter 3's checklist question 1 named for logic bugs — passing a check is not the same claim as being correct — applied here to a single line's API surface instead of a whole feature's behavior.

3. Is there a suspiciously confident comment explaining "why" the call works? This is a softer signal, but a real one: a comment like # simplified — pass through directly or # ignore_na skips missing-date rows cleanly attached to a hallucinated call is not evidence the call is correct — it's often the model's own plausible- sounding gloss on a plausible-sounding call, generated by the exact same mechanism that generated the call itself. A comment explaining why a line does something is not independent verification that it actually does that thing; it's more text from the same source, conditioned on the same probability distribution. Treat a suspiciously tidy explanation as a reason to check harder, not as the check itself.

All three of these are variations on one move: stop reading the code as prose and start treating it as a claim to be tested against the actual, installed, real thing it references. That's strictly cheaper than it sounds — hasattr() and a real function call both take seconds, and both are unambiguous in a way "does this look right" never is.

Logical Bugs: Correct API, Wrong Logic

Not every wrong line is a hallucination. A logical bug uses real, correctly-spelled, correctly-called functions and methods — every name checks out against dir(), every call runs without raising — and is still wrong, because the reasoning connecting those correct calls together is broken. This is, in a specific sense, harder to catch than a hallucinated API: there is no dictionary lookup, no hasattr() check, no import error that surfaces it. Catching a logical bug requires actually tracing what the code does with real values, not checking whether the code is allowed to exist.

Off-by-one and boundary errors. A function documented as excluding today's date includes it anyway, because a comparison operator is one character off from what the docstring promises:

a boundary that contradicts its own docstring 
def week_range(as_of):
    """Return the 7 days strictly before as_of -- not including
    as_of itself, since today's numbers are still accumulating."""
    start = as_of - timedelta(days=7)
    return start, as_of

def filter_week(records, as_of):
    start, end = week_range(as_of)
    return [r for r in records if start <= r["date"] <= end]
    #                                  ^^                  ^^
    # both bounds inclusive -- pulls in 8 days, not 7, and
    # includes as_of itself despite the docstring's own promise

Every function name here is real. timedelta, list comprehension, comparison chaining — nothing here would fail a hasattr() check or raise on import. The only way to catch this is to compute what it actually returns for a specific, concrete as_of and compare against what the function's own stated contract promises.

Inverted or wrong boolean logic. A condition that reads almost right, checked against exactly one case that happens to pass:

a condition that's backwards for the case that matters 
def is_eligible_for_discount(customer):
    # Eligible if NOT a first-time buyer and account is in good standing
    return customer.is_first_purchase or not customer.account_in_good_standing
    # should be: not customer.is_first_purchase and customer.account_in_good_standing
    # -- as written, first-time buyers get the discount (backwards),
    # and it ALSO grants it to accounts in bad standing (backwards again)

This runs cleanly, returns a real boolean, and will pass any test that only checks a returning customer in good standing — because that specific case happens to evaluate correctly by coincidence, not because the logic is right. Read the comment above the code and the code disagree with each other in exactly the way a hallucinated API's confident comment can disagree with what a call actually does; the difference is that here, both the comment and the code are individually sensible-sounding, and only comparing them against each other and against a boundary case (a first-time buyer in good standing) surfaces the bug.

Mutating a shared object nobody intended to share. Python's mutable-default-argument gotcha, still common in agent-generated code because it's a plausible, common pattern that happens to be wrong:

a default argument that leaks state across calls 
def build_message(csv_path, recipients, headers={}):
    # headers defaults to {} per call -- looks safe
    for k, v in DEFAULT_HEADERS.items():
        headers.setdefault(k, v)
    headers["X-Report-Sent"] = "true"
    return headers
# {} is evaluated ONCE, at function definition time, not per call --
# every call that doesn't pass its own headers mutates and shares
# the SAME dict object. The second call sees "X-Report-Sent" already
# set from the first call, before it has actually sent anything.

Nothing here is a hallucinated call — dict.setdefault is real, correctly used. The bug is a specific, well-known mismatch between what the syntax looks like it does (a fresh empty dict every call) and what Python's actual evaluation-order semantics do (one dict, created once, reused and mutated across every call that hits the default). It's exactly the kind of thing that survives a single-call smoke test and only shows up once the function has been called more than once in the same process.

What is... wrong operator precedence, as a fourth category? A related, equally invisible-to-import-checks bug: writing if user.is_admin or user.is_owner and resource.is_shared: when the intent was "an admin, or an owner of a shared resource" — but and binds tighter than or in Python (and in most languages), so this actually parses as user.is_admin or (user.is_owner and resource.is_shared), which happens to be what was intended here, but is a trap the instant someone reorders the clauses without adding parentheses. Precedence bugs are dangerous specifically because the code is completely valid, runs without error, and is sometimes accidentally correct — which is worse than being reliably wrong, because it survives testing until the one input combination that exposes the difference finally shows up.

Building the Validate-Before-Trust Habit

This chapter isn't a sixth and seventh checklist question bolted onto Chapter 3's five — it's Chapter 3's questions 1 and 5, applied with more mechanical precision to exactly the failure modes this chapter names. Question 1 ("does it actually match the acceptance criterion, not just pass it") is precisely what the hook's ignore_na diff and the mutable- default-argument example both defeat: a test suite that doesn't happen to exercise the exact line or the exact second call where the bug lives will report green regardless. Question 5 ("could this be a symptom fix instead of a root-cause fix") applies directly to the boolean-inversion example — a test written against the one case that happens to work is a symptom-level check, not a root-cause one, the same distinction Chapter 3 drew for the invoice-rounding bug.

What this chapter adds isn't a new question — it's a specific, practiced answer to "how do I actually check this," for the two failure shapes a checklist question alone doesn't tell you how to catch: run the exact call against the real library (hallucinated APIs), and trace the exact values through the exact logic for a boundary case, not just the obvious case (logical bugs).

The stakes connect directly to Chapter 5's central warning. A hallucinated API accepted as real, or a logical bug accepted as correct because "the code looks confident and the test passed," becomes exactly the kind of settled-but-unverified fact Chapter 5 described going off the rails: once ignore_na=True is treated as a real, working argument, every later turn — and every later reviewer, including a future you — inherits that false premise without re-checking it. Nothing in a clean diff, a passing test, or a confident commit message marks the difference between "this was actually verified" and "this looks like something that was verified." That's true for the model producing the code and equally true for a human skimming it afterward. The fix in both cases is the same: get an independent, mechanical fact into the loop — hasattr(), a real function call, a traced boundary case — before treating anything as settled.

GenAI Builder Thought Process

Problem: a reviewer approves a diff because "it's well-formatted, uses real-sounding library calls, and the named test passed," then the code raises an exception, or silently misbehaves, the first time it runs against a code path the test didn't cover.

Assumption being made: that code which looks like it was written by someone who knows the library well is evidence the calls in it are real, and that a passing test proves every line in the diff was actually exercised and correct — rather than evidence that the specific lines the test happens to touch behaved as expected.

What actually distinguishes a genuinely validated diff: not confidence of tone, not code style, not whether the reviewer personally recognizes the library — whether every claimed API call was checked against the real, installed library (hasattr(), an actual call with real arguments) and whether the actual logic was traced through a boundary case, not just the case the test happens to cover.

Why this matters for Module 4's project below: the flawed PR you're about to review was built specifically so that a fast, surface-level read — "the file list matches the task, the code looks like real pandas/csv/email code, there's a docstring explaining the intent" — passes cleanly, while every one of its planted flaws only surfaces under the two checks this chapter actually teaches: run the exact call, and trace the exact boundary.

Working definition to carry forward: detecting a hallucinated API or a logical bug means treating every unfamiliar or load-bearing line of an agent's diff as an unverified claim, and closing that claim with a mechanical check — introspection or an actual run for API existence, a traced concrete value for logic — before trusting it, exactly the discipline this course's own build process has applied to every code example in every prior chapter.

Points To Remember

  • A hallucinated API is a call, method, or argument that looks exactly as plausible as a real one because it was generated by the same "most probable continuation" mechanism Chapter 4 described — not a typo, and not correlated with how confident the surrounding code or comments sound.
  • Hallucinations cluster around less-common libraries, APIs that changed after training data, and calls that borrow a chaining/fluent pattern from a more commonly-seen library that the actual one doesn't support.
  • Catch a hallucinated API mechanically: check the name against the real library with hasattr()/dir(), actually run the exact call with real arguments rather than just importing the module, and treat a suspiciously confident explanatory comment as a reason to check harder, not as verification.
  • A logical bug uses entirely real, correctly-spelled, correctly-called APIs and is still wrong — off-by-one/boundary errors, inverted boolean logic, and mutable-default-argument state leaks all run cleanly and can pass a test that doesn't happen to exercise the exact wrong path.
  • Logical bugs are harder to catch than hallucinated APIs precisely because there's no dictionary lookup that catches them — only tracing actual values through the actual logic, for a boundary case, not just the obvious one.
  • This chapter is Chapter 3's questions 1 and 5, made mechanically specific to API and logic correctness — and a hallucinated call or wrong logic accepted as "it must work, it looks confident" is exactly the settled-but-unverified premise Chapter 5 warned compounds silently once later work builds on top of it.
