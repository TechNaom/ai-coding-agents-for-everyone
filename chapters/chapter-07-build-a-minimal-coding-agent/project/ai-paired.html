Chapter 7 — Pair With an AI, Then Critique It 20 min

Pair With an Agent to Extend the Reference Implementation

Step 1: You just read a working agent, not built one solo yet

There's no solo build for this chapter — that's Chapter 8's job, once file/shell/git tools get real depth. What you do have, right now, is a real reference agent (starter.py) you've read and can run. This page has you use an actual coding agent tool — Claude Code, Cursor, or GitHub Copilot's agent mode, your choice, per Module 1 — to extend it with one small new capability, and then review what comes back the way Chapter 3 taught, not the way a beginner would.

Step 2: Pair with an agent

Here's a real prompt you could hand a coding agent, pointed at your own copy of starter.py:

the-prompt.txt 
Add a fourth tool to this minimal agent, called list_files, that
lists the contents of a directory inside the workspace. Follow the
exact same pattern as the other three tools: a TOOLS schema entry,
a plain function, and a TOOL_FUNCTIONS dispatch entry. Keep the
change minimal -- don't touch anything else in the file.

And here's a plausible response — the kind of diff a real coding agent might hand back on the first try. Read it as if it just landed in front of you, before scrolling to the critique below. (This is exactly the diff sitting in this chapter's own project/solution.py right now, if you want to open it side by side with starter.py.)

the-agent's-diff (list_files addition) 
+    {
+        "type": "function",
+        "function": {
+            "name": "list_files",
+            "description": "List a directory's contents.",
+            "parameters": {
+                "type": "object",
+                "properties": {
+                    "path": {"type": "string", "description": "Path relative to the workspace root"}
+                },
+                "required": ["path"],
+            },
+        },
+    },

+def list_files(path):
+    return os.listdir(path)

 TOOL_FUNCTIONS = {
     "read_file": read_file,
     "write_file": write_file,
     "run_shell_command": run_shell_command,
+    "list_files": list_files,
 }

It runs. It matches the ask ("a fourth tool, same pattern"). It's also wrong in three separate, genuinely easy-to-miss ways — exactly the kind of diff Chapter 3 warned you a green test run and a quick skim both miss.

Step 3: Where did the agent's diff lie to you?

Click to see the critique, walked through Chapter 3's five questions
Question 2 — did it touch anything outside the stated boundary?

What it looks like it does: list_files(path) is one line, calling a standard-library function with the exact argument name (path) every other tool in this file uses. Nothing about it looks dangerous at a glance.

What it actually does: every other tool in starter.py — read_file, write_file, run_shell_command (via its fixed cwd=WORKSPACE) — routes its path through _safe_path(), which rejects anything that would resolve outside WORKSPACE. list_files calls os.listdir(path) directly, with no confinement at all. Ask the agent to list "../../etc" or an absolute path like "/etc", and it will happily return real contents of a directory well outside the workspace this agent was supposed to be scoped to — the exact boundary escape Chapter 2's boundaries and Chapter 3's checklist both exist to catch, now baked into a tool a future task might call without anyone reviewing that specific call.

The fix: route path through _safe_path() exactly like the other three tools do — os.listdir(_safe_path(path)).

Question 4 — does it introduce patterns inconsistent with the rest of the file?

What it looks like it does: the tool's description, "List a directory's contents," reads like ordinary, reasonable tool documentation — short and to the point, the same style as the other three tools' one-line descriptions.

What it actually does: it never says the argument has to be a directory, not a file, and it doesn't distinguish itself from read_file's description ("Read the full contents of a text file...") clearly enough for the model to reliably tell them apart on an ambiguous request like "show me what's in billing/." Chapter 4 already established exactly this failure: two tools with similar, under-specified descriptions get confused for each other, and the model fills the resulting gap with a guess — not a hypothetical here, it's a real property of this specific diff's wording.

The fix: tighten the description to something like "List the names of files and subdirectories directly inside a directory (not a file) in the workspace," which disambiguates it from read_file the same way run_shell_command's description already disambiguates itself from both.

Question 4, again — a second inconsistency, easy to miss because nothing crashes

What it looks like it does: a one-line function body, calling a function that either returns a list or raises — normal Python, nothing alarming.

What it actually does: read_file catches its own likely failure (FileNotFoundError) and returns a clean f"error: no such file: {path}" string — a deliberate, established pattern in this file for how a tool reports its own expected failure back to the model. list_files does none of that; a missing directory raises straight through to dispatch_tool_call's generic except Exception handler, producing a vague, inconsistent message shaped like Python's own exception text instead of the file's established "error: ..." convention. Nothing crashes end to end — dispatch's safety net catches it — but the diff quietly broke a pattern the rest of the file bothered to establish on purpose.

The fix: wrap the call and return a matching message: try: return os.listdir(_safe_path(path)) except FileNotFoundError: return f"error: no such directory: {path}".

Questions 1, 3, and 5 — worth checking and coming up clean here

The diff does match what was asked (Q1 — a fourth tool, same shape) and every line has an obvious one-sentence justification (Q3 — nothing unexplained sneaks in). It's not a symptom-fix-for-a- root-cause situation (Q5 — there's no bug being masked here, just a missing tool being added). That's worth noticing too: a diff can cleanly satisfy three of five questions and still be genuinely unsafe to merge on the other two. Reading only far enough to feel satisfied is exactly the habit Chapter 3 warned against.
