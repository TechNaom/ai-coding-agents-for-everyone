Chapter 6 Practice Bank ~18 min

Practice Bank: Context Windows and Codebase-Scale Understanding

Short scenarios, one judgment question each — practice spotting context pressure and codebase-scale limits in situations where nothing has technically gone wrong yet.

Scenario · "It has plenty of room left"

The token counter says 30% full

A teammate checks a long-running session's token usage against the model's context window: "We're only using 30% of the window, so context definitely isn't the issue with this weird behavior we're seeing." The session has run 90 turns, and an early convention stated once on turn 5 is being violated on turn 85. Is the teammate right that context "isn't the issue" here? Explain using this chapter's distinction.

Scenario · The "helpful" full-repo dump

"I'll just give it everything so it has full context"

Before assigning a bug fix, a developer pastes the contents of every file in the affected module — twelve files, most unrelated to the actual bug — reasoning that "more context can only help." Only one of the twelve files is where the fix will actually go. Explain what this choice costs for the rest of the session, even if the agent does eventually find the right file.

Scenario · The onboarding assumption

"It's been in this repo all week, it should know"

A tech lead is frustrated that an agent, on a fresh session, doesn't know the team's convention of always using the internal Money type instead of raw floats for currency — a convention that's been enforced in code review for months and that every human engineer on the team knows by heart. The agent used a raw float. Explain why "it should know by now" doesn't apply here, and what would have actually gotten that convention in front of the agent for this session.

Scenario · The compaction that lost the caveat

The summary that dropped the exception

A harness's auto-generated summary of a long session's early turns reads: "Migrated all API routes to the new auth middleware." The actual early turns, now summarized away, showed one route (/webhooks/stripe) was explicitly and deliberately excluded because it uses a different auth scheme entirely. A later turn, working only from the summary, "fixes" that route to match the others. What specifically went wrong, and where in the pipeline (not "the AI made a mistake") would you look to prevent a repeat?

Scenario · Restart or push through

Four hours in, still going

An agent has been working unattended for four hours on a large test-suite migration. It's still making edits and running tests, no errors, no step cap hit. A teammate asks whether you should just let it keep running since "it hasn't failed." What would you actually want to look at in the recent transcript before answering, and why isn't "it hasn't thrown an error" sufficient on its own?

Scenario · The search that never happened

Confidently wrong about something searchable

Asked to "add the new discount tier to the pricing logic," an agent immediately writes a new pricing/discounts_v2.py file and implements the tier there, without ever running a search for existing discount-related code. It later turns out pricing/discounts.py already exists with three other tiers implemented, unseen this session. Using this chapter's codebase-scale section, explain precisely why this happened — not "the agent should have known," but what specifically was missing from this session that a search-first step would have supplied.
