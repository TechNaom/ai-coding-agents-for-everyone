Chapter 8 Practice Bank ~24 min

Practice Bank: Giving Your Agent File/Shell/Git Tools

Short scenarios, one judgment question each — plus a small runnable script (starter.py / solution.py in this folder) that runs the same eight shell commands through both a denylist checker and an allowlist checker, so you can see this chapter's central trade-off concretely instead of just reading about it. Predict, then run, then work through the scenarios below.

Scenario · Trusting the wrong thing

The confident summary

An agent runs write_file to update a 300-line config file, then confidently reports "updated the timeout value, everything else preserved." What's the one tool call you'd want this agent to make next before you trust that sentence, and why does that connect directly to this chapter's edit_file section?

Scenario · Review

The silently-successful list_files

A coworker's list_directory implementation passes every manual test they tried — it correctly lists workspace subdirectories every time. It also, on one call during your review, happily returns the contents of / when a teammate passed "/" as the path by mistake. What does that tell you about the difference between "passed every test I tried" and "actually safe," and what's the one-line fix?

Scenario · The ambiguous edit

Which "return None" did you mean?

An agent is asked to "fix the bug where the function returns None instead of the result" in a file with three functions, two of which correctly and intentionally return None. It calls edit_file with find="return None". Walk through exactly what happens with this chapter's edit_file implementation, and explain why that outcome is actually the safe one, even though it doesn't fix the bug on the first try.

Scenario · Shell hardening

The command that technically isn't on the list

A teammate tests the denylist by running rm -rf / (blocked, as expected) and then declares the denylist "proven safe." What's a single different command — not identical to anything in SHELL_DENYLIST, but just as capable of doing real damage inside the workspace — that would sail straight through unblocked? What does that prove about what "tested" actually means for a denylist specifically?

Scenario · The git_commit pitch

"It's just a commit, we can always revert"

A teammate wants to add an autonomous git_commit tool, arguing that since git revert exists, nothing is really at risk. Using this chapter's distinction between "recoverable" and "reviewed before it happens," explain what actually gets lost even in a fully revertible autonomous commit, and why that's a different question from whether the change itself was technically correct.

Scenario · Choosing the right checker

General-purpose agent vs. narrow CI runner

This chapter's reference agent uses a denylist for run_shell_command. A CI-troubleshooting agent that only ever needs to run pytest, git status, and a handful of known linters is being designed separately. Which checker — denylist or allowlist — fits the CI agent better, and what specifically about its task (not just "it's for CI") makes that the right call, using this chapter's own reasoning rather than a general "allowlists are always safer" claim?

Scenario · Scoping a task

The vague cleanup task, revisited

Same setup as Chapter 7's practice bank: a learner passes the task "clean up the workspace" to this chapter's extended agent, which now also has edit_file and git_status available. Does having those extra tools make the vague task safer, riskier, or unchanged compared to Chapter 7's three-tool version — and why, specifically?
