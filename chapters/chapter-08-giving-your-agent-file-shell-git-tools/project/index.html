Chapter 8 Project ~30 min · Level 2 — Assisted

Project: Extend the Agent With One New Tool of Your Own

This is the real thing — Module 3's Level 2 (Assisted) project, the one both of Chapter 7's project pages pointed forward to: "extend a provided minimal agent with one new tool, partial scaffold," per docs/curriculum/CURRICULUM_MAP.md. It waited for this chapter on purpose. Shipping it before Chapter 8 would have meant asking you to design a new tool's safety boundaries before you'd actually seen what those boundaries need to guard against — the exact reasoning Chapter 7's own preview page gave. Now you have: edit_file's ambiguous-match refusal, list_directory's type-distinguishing errors, git_status/git_diff's read-only-by-construction safety, and run_shell_command's honest, partial denylist. This project asks you to apply that same discipline to a tool you design and build yourself.

What's provided

starter.py is Chapter 7's reference agent — the loop, dispatch_tool_call's defensive handling, none of it changed — extended with everything this chapter built: edit_file, run_shell_command hardened with a denylist, and the read-only git_status/ git_diff pair. All five of those tools are fully implemented, tested, and not your job to touch.

Your task

Add one new tool of your own choosing, following the exact four-step pattern every tool in starter.py already uses (a schema entry, a _safe_path()-routed function, clean "error: ..." strings for expected failures, a TOOL_FUNCTIONS registration). Two # TODO markers in starter.py show you exactly where. The module docstring at the top of the file has five concrete ideas if you want a starting point — but picking your own is genuinely fine, and arguably better practice than following a suggested list.

What "done" looks like A new tool that (1) has a schema entry with a description precise enough to distinguish it from every other tool in the file — the same precision this chapter's list_directory section discussed at length — (2) routes any path argument through _safe_path() with no exceptions, (3) returns a clean, descriptive error string for every expected failure case instead of letting an exception fall through to dispatch_tool_call's generic handler, and (4) is registered in TOOL_FUNCTIONS. solution.py shows one fully worked example (list_directory) if you want a reference — see README.md for exactly how to verify your own tool works, both by calling your function directly (no live model needed) and by running the full agent against a real local model.

Then: review your own diff

Before calling it finished, apply Chapter 3's five-question checklist to your own change — specifically question 2 (did it touch anything outside the stated boundary?) and question 4 (is it consistent with the rest of the file's patterns?). Those are exactly the two questions Chapter 7's AI-paired list_files tool failed, and exactly the two this project is designed to test whether you now catch in code you wrote yourself, not just code you're critiquing.

Why this is the right project for right now

You've now seen four different tools get built with real, specific care about failure modes — an ambiguous edit refused instead of guessed, a missing directory distinguished from a wrong-type path, two read-only git tools made structurally safe by how they call subprocess, and a shell tool with an honestly-limited denylist instead of an oversold "safe" claim. This project isn't asking you to invent that discipline from nothing — it's asking you to apply a pattern you just watched built four times, on a fifth tool that's entirely yours.
