Chapter 4 Interview Questions ~15 min

Interview Questions: The Agentic Loop: Plan, Act, Observe, Repeat

Grouped by level. Each includes a strong answer, a red flag, and a follow-up.

1. (Beginner) What is a "tool call," mechanically, and how is it different from the model just writing a sentence?

Strong answer: A tool call is a structured piece of model output — a tool name plus a JSON object of arguments — produced by exactly the same mechanism as any other text: token-by-token prediction of the most probable continuation given everything currently in the model's input. It only looks different from prose because of its shape. What actually makes it an "action" and not just more text is what happens after: the harness reads it and executes a real function with real side effects, independent of what the model predicted would happen.

Red flag: Describes a tool call as the model "deciding to take an action" via some separate reasoning or planning module distinct from ordinary text generation, as if tool selection were a different kind of computation than producing a sentence.

Follow-up: "If a tool call is produced the same way as any text, what stops the model from hallucinating a tool that doesn't exist?"

What this proves: Understands that "acting" is a data-shape and harness-execution distinction, not a different underlying mechanism inside the model.

2. (Beginner) Why can't the model "watch" a tool run, and what does it actually experience instead?

Strong answer: The model is stateless between turns — it has no background process it's aware of while a tool executes. What "observing" actually means is that a new block of text (the tool result) gets appended to the conversation, and on its next turn the model re-reads the entire conversation from scratch, including that new block, and produces one more prediction. The apparent "noticing" of a discovery is just a fresh prediction over an input that now contains new text.

Red flag: Describes the model as having ongoing awareness or memory of a tool "running in the background," or says it perceives the tool result "as it happens" rather than reading it fresh on the next turn.

Follow-up: "Given that, what does it mean for an agent to 'forget' something it read five turns ago?"

What this proves: Has internalized the stateless, re-read-from-scratch nature of each turn rather than a human-memory mental model.

3. (Intermediate) Two tools do similar things but are described ambiguously to the model. What goes wrong in practice, and why?

Strong answer: Since tool selection has no separate router — the model predicts a tool-shaped block whose name and arguments match one of the tool descriptions it was given up front — ambiguous descriptions mean the model has to guess which tool the description was pointing at, the same way a vague prompt produces guesswork instead of a targeted answer. The result is the wrong tool getting called, or the right tool getting called with vague or invented arguments, because the model is filling a gap with its best statistical guess rather than looking up a certain fact.

Red flag: Treats tool confusion as a "bug in the model" rather than a predictable consequence of underspecified tool descriptions — the same class of problem as an underspecified prompt.

Follow-up: "What would you change in a tool's description to reduce this kind of confusion, without changing what the tool does?"

What this proves: Connects tool-description quality to Chapter 2's prompting-precision lesson rather than treating it as an unrelated engineering detail.

4. (Intermediate) Name the (at least) four ways an agent loop can stop, and explain why it matters, during review, which one actually happened.

Strong answer: A clean stop (a turn with no tool call — the model believes it's done), a hard stop (a harness-enforced step cap overriding the model), a boundary stop (an explicit rule blocking or redirecting a call), and a failure stop (an unrecoverable tool error). It matters because each implies a different kind of scrutiny: a clean stop is a prediction, not a verified fact, so the acceptance criterion still needs independent checking; a step-cap stop means the task may be genuinely incomplete, not "done"; a boundary stop means the harness intervened, not the model choosing correctly; a failure stop means something broke and the model's response to that failure needs its own review.

Red flag: Treats every stop as equivalent to "the agent finished successfully," or can only name one or two of the four without recognizing there's more than one mechanism.

Follow-up: "How would you tell, just from a transcript, which of the four actually happened?"

What this proves: Can distinguish termination mechanisms and connect that distinction to Chapter 3's "don't trust the agent's own 'done' message" review discipline.

5. (Senior) You're deciding between an upfront-multi-step-plan architecture and a reactive, turn-by-turn architecture for a new coding agent. What's the real trade-off, and how would you decide?

Strong answer: An upfront plan is predictable and easy for a human to audit mid-task — you can read a checklist and know roughly where the agent is — but it's brittle against genuine discoveries: it has to be explicitly detected as wrong and revised when reality contradicts an assumption baked into it early. A reactive loop, where each turn's plan is simply the best next action given the full history so far, adapts naturally to new information because there's no stale plan object to revise, but it's harder to audit mid-flight since there's no fixed plan to compare the current action against. The decision hinges on how volatile the task's discovery surface is (a lot of unknowns favors reactive) versus how much mid-task human auditability matters (compliance-heavy or long-running tasks favor a visible, even if non-binding, checklist as a hybrid).

Red flag: Declares one approach strictly superior without naming the specific trade-off (auditability vs. adaptability), or claims real agents never use any upfront structure at all.

Follow-up: "How would a visible to-do list, as a non-binding artifact rather than a governing structure, capture some of both approaches' benefits?"

What this proves: Can reason about an architectural trade-off rather than treating "planning" as a single, undifferentiated feature.

6. (Senior) A teammate says "the agent changed its mind when it saw the existing rate_limit decorator." Rewrite that sentence in terms of the actual mechanism, and explain why the rewrite matters for debugging.

Strong answer: A tool result containing the decorator's file location was appended to the conversation; on the next turn, the model re-read the entire conversation including that new block and produced a different prediction because the input was different — nothing "changed" inside the model between turns, there's no persisted intention that got revised. This matters for debugging because if you believe the agent has ongoing awareness or intent, you'll look for a bug in "reasoning" when something goes wrong; if you know it's stateless prediction over a growing input, you look at exactly what text was and wasn't in context at the turn in question, which is where the actual answer usually lives.

Red flag: Can't translate the human-sounding sentence into the mechanistic one, or insists the human framing is "basically the same thing, just simpler language" without seeing that it implies a different, wrong debugging strategy.

Follow-up: "Given this, what's the first thing you'd inspect when an agent 'ignores' an instruction from ten turns ago?"

What this proves: Translates folk-psychological descriptions into the mechanism this chapter teaches, and connects that translation to practical debugging habits.

7. (Architect) Design the stop-condition policy for a coding agent that will run unattended in CI. Which of the four stop types do you need to make maximally strict, and why?

Strong answer: The hard stop (step cap) and the boundary stop need to be the strictest and most mechanically enforced, since unattended means no human is present to catch a clean stop that's actually a wrong "I'm done" prediction, or a failure stop that got silently misrouted. Concretely: a conservative step cap sized to the task's expected complexity, boundaries enforced by the harness refusing to execute a disallowed tool call (not just a prompt-level instruction the model might override), and every clean stop gated behind an independently-run acceptance check before the pipeline treats the task as actually done — never trusting the model's own no-tool-call turn as proof of completion. Failure stops should fail the pipeline loudly rather than let the loop guess its way past an error.

Red flag: Proposes relying on the model's own judgment for when to stop as sufficient for an unattended CI context, or doesn't distinguish harness-enforced boundaries from prompt-level instructions that a sufficiently determined next-token prediction could route around.

Follow-up: "How does this policy change, if at all, once Chapter 6's context-window limits enter the picture on a long-running CI task?"

What this proves: Designs for the unattended, high-stakes case by hardening exactly the stop conditions a human isn't present to backstop — direct groundwork for Module 5's CI chapter.

8. (Architect) An agent team wants to move from the upfront-plan architecture to the reactive architecture to improve adaptability, but is worried about losing auditability for compliance reasons. How would you resolve this without picking one extreme?

Strong answer: Recognize that the visible to-do list most real coding agents already produce is exactly this resolution: it's a non-binding artifact, not a governing plan object, so it doesn't reintroduce the brittleness of a plan the loop is obligated to follow, but it gives a human (or an automated compliance check) something concrete to read against the agent's actual turn-by-turn actions after the fact. The audit trail comes from logging every turn's actual tool call and result — the true record of what happened — with the to-do list as a human-readable index into that log, not a replacement for it.

Red flag: Proposes reverting to a strictly-followed upfront plan purely to satisfy compliance, reintroducing the exact brittleness the team was trying to escape, or dismisses the compliance concern as unimportant.

Follow-up: "What would you log at each turn to make a post-hoc audit possible without slowing down the loop itself?"

What this proves: Resolves an apparent architectural conflict by separating "governing structure" from "audit artifact" — systems-level thinking about how the loop's mechanism interacts with organizational requirements.
