Chapter 1 Beginner ~18 min

Why Coding Agents Aren't Just Autocomplete

"It's just fancier autocomplete" is the single most common way people underestimate what a coding agent can do — and the single most common reason people get frustrated when it does something they didn't expect. This chapter builds the real distinction before you write a single prompt.

Two developers, same afternoon, same ticket: "the CSV export is missing the new `region` column — add it, and make sure the existing tests still pass."

Developer A has an inline-suggestion tool — the kind that watches the cursor and proposes the next few lines as you type. They open the export function, start typing the new field mapping, and the tool suggests a plausible line. It's a good suggestion — it saved some keystrokes. But Developer A still has to find which file defines the CSV headers, notice there's a second place headers get validated, remember to check the test file, run the tests, read the failure, and fix the one they forgot. The tool helped at each keystroke. It did not know a second place existed.

Developer B opens a coding agent and types roughly the same request in plain English. What happens next looks nothing like autocomplete: the agent searches the repo for where CSV headers are defined, opens the export function, opens the file that validates headers (which Developer A didn't know about until the tests failed), edits both, runs the test suite itself, reads the failure output, and fixes a second file it discovers is responsible for the failing test — all before showing Developer B anything to review. Same ticket. Completely different shape of work.

Where Autocomplete's Ceiling Actually Is

This isn't a knock on autocomplete-style tools — GitHub Copilot's original inline suggestions and IDE features like IntelliSense are genuinely useful, and most engineers who've used them well know exactly what they're good at: predicting the next few tokens given the code immediately around the cursor. That's a real, bounded job, and they do it fast.

The ceiling shows up the moment a task needs information the tool doesn't have in front of it. Inline suggestion tools generally see the current file (and sometimes a few open tabs) — they don't go searching the rest of the repository for a second file that validates headers, they don't run your test suite, and they certainly don't read a failing test's output and go fix the actual cause. Every one of those steps still lands on the human, one keystroke or one file at a time.

What is... autocomplete-style suggestion? A tool that predicts likely next tokens or lines based on immediate local context (the current file, cursor position, recent edits) and proposes them inline as you type. It is reactive to your keystrokes and scoped to what's visible around the cursor — it does not decide what to look at next, run commands, or judge whether its own suggestion actually solved the problem.

That single sentence — "it does not decide what to look at next" — is the whole gap this chapter is about. Autocomplete predicts. An agent decides.

The Plan / Act / Observe / Repeat Loop

What actually happened during Developer B's afternoon wasn't one big prediction — it was a sequence of small, deliberate cycles. Naming that sequence is the single most useful mental model in this entire course, because every coding agent you'll ever use — Claude Code, Cursor's agent mode, GitHub Copilot's agent mode — runs some version of it:

  • Plan: given the request, decide what to do next. Not the whole solution up front — usually just the next concrete step ("first, find where CSV headers are defined").
  • Act: actually do that step using a real tool — search the codebase, read a file, run a shell command, or edit code. This is the part that has no autocomplete equivalent: the agent is not predicting text, it's calling a function that has a real effect (a file gets read, a command gets executed).
  • Observe: look at what the tool actually returned — the search results, the file's contents, the test runner's output — and treat that as new information, not as a guess to move past.
  • Repeat: decide the next step based on what was just observed, which might be totally different from what was planned before that observation. Finding the second header-validation file wasn't in the original plan — it showed up because the agent ran the tests and read a failure it didn't expect.

Notice what makes this different from "a bigger, smarter autocomplete": the loop can change direction mid-task based on something it discovers, without a human re-typing a new prompt for every discovery. Developer A would have needed to notice the second header file themselves, then go ask the tool (or write it themselves) to fix that file too. Developer B's agent noticed it because observing a failed test was part of its own loop, not a separate errand for the human.

What "Autonomy" Actually Buys You (and Costs You)

"Autonomy" here has a specific, narrow meaning worth being precise about: the agent can complete several plan/act/observe cycles in a row — reading multiple files, running a command, editing more than one file, re-running a check — without a human approving each individual keystroke or file read along the way. It does not mean "unsupervised forever" or "trusted blindly." Most agent tools still let you review the full set of changes before anything is committed, and later chapters (2 and 3 especially) are built almost entirely around how to scope that autonomy and review its output well.

export.py — before the agent's turn 
def csv_headers():
    return ["id", "name", "amount", "created_at"]

def _validate_headers(headers):
    # duplicated on purpose in this codebase's legacy export module
    expected = ["id", "name", "amount", "created_at"]
    if headers != expected:
        raise ValueError("header mismatch")

This is the second file Developer A didn't know existed. An autocomplete tool sitting in export.py would never surface it — it isn't in view. An agent that ran the test suite as part of its own loop hit the ValueError, read the traceback, opened _validate_headers, and updated the expected list too — a second file edit that happened because the agent observed a real failure, not because it predicted the next line of a file a human had open.

That's the trade being made: fewer individual approvals in exchange for a tool that can act on what it discovers. It's a real capability upgrade, and it's also exactly why "review the diff like you'd review a colleague's PR" (Chapter 3) matters more with an agent than it ever did with inline suggestions — the agent touched more files, on its own judgment, than a human typing keystroke-by-keystroke ever would in the same amount of time.

GenAI Builder Thought Process

Problem: a learner keeps saying "I already use Copilot, so I already know how coding agents work" — and gets surprised the first time an agent edits three files they never opened.

Assumption being made: that "AI writes code for me" is one capability with different brand names, rather than two structurally different things — a single prediction versus a loop that decides its own next step.

What actually distinguishes them: not "smarter," not "bigger model" — specifically, whether the tool can call real tools (search, read, run, edit) and use what comes back to decide its next move, across more than one step, without a human re-prompting after every discovery.

Why this matters before Chapter 2: you can't scope a task for an agent well (Chapter 2) or review its diff like a senior engineer (Chapter 3) if you're still mentally modeling it as "autocomplete that got lucky." The habits that work for reviewing one suggested line don't scale to reviewing a five-file change the agent made on its own initiative.

Working definition to carry forward: an agent is a system that runs plan/act/observe/repeat using real tools, across multiple steps, with autonomy over how many steps it takes before showing you the result — not a single smarter prediction.

Points To Remember

  • Autocomplete-style tools predict the next few tokens from local context and hand control back to you after every suggestion — they don't decide what to look at next.
  • A coding agent runs a plan/act/observe/repeat loop: it picks a next step, uses a real tool (search, read, run, edit), reads what that tool actually returned, and decides its next step from that new information.
  • The "act" step is the structural difference — it's a real effect (a file gets read or edited, a command actually runs), not a text prediction a human still has to apply.
  • Autonomy means completing several loop cycles without per-keystroke approval — it does not mean unsupervised forever; reviewing the result well is still the human's job (Chapter 3).
  • The practical tell: if a tool only ever changes what's visible around your cursor, it's autocomplete. If it can discover something (like a second file) mid-task and act on that discovery on its own, it's running an agent loop.
