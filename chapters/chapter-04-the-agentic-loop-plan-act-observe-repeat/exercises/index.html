Chapter 4 Exercises ~30 min

Exercises: The Agentic Loop: Plan, Act, Observe, Repeat

Still conceptual — no SDK or code execution here, that starts in Module 3. Each exercise hands you a short transcript fragment or turn-by-turn scenario; the work is tracing the mechanism precisely — what was in context, what got predicted, and why — not guessing at what "felt" right.

Exercise standard Six tasks below. At least three are production-gear: harder, ambiguous, real-world judgment calls rather than clean textbook cases.

1 Turn 1, unpacked

Here is a single model turn, as literal data:

{
  "role": "assistant",
  "content": [
    { "type": "text",
      "text": "I'll check the test file to see the exact
               expected error message before changing anything." },
    { "type": "tool_use",
      "id": "call_9",
      "name": "read_file",
      "input": { "path": "tests/api/test_export.py" } }
  ]
}

Identify, separately: (a) what the model produced, (b) what has and hasn't happened in the actual codebase at this exact point, and (c) what determines whether the harness treats this as a valid, executable request.

2 Which tool, and why

The agent has these tools, described to it up front:

list_files(directory: string)
  "List file and directory names one level under the given path."

grep_codebase(pattern: string)
  "Search file contents for a regex pattern across the repo."

read_file(path: string)
  "Read the exact contents of one file. Requires an exact path."

The task is: "The error message 'Invalid export format' appears somewhere in the codebase — find where it's raised and add a new branch for the 'xlsx' format." At the very first turn, nothing else is in context yet. Which tool does the model most likely call, and why does calling read_file at this exact point require information the model doesn't have?

3 Name the stop

Four short transcript endings, each cut off right after the last thing that happened:

  1. The model's final message contains only text: "All three tests now pass and the diff matches the acceptance criterion."
  2. The harness's log shows: "step_count: 40/40 — forcing stop before next tool call".
  3. The model attempts a tool call to run_shell("rm -rf build/"); the harness's log shows "blocked: destructive command outside allowed list", and the model's next turn is text asking the human to confirm.
  4. The model calls run_tests; the tool result is "Error: test runner exited with signal 9 (OOM), no output captured", and the next several turns keep calling run_tests again with no change in outcome.

Name which of the four stop mechanisms from the lesson each one is (or, for (d), name what's actually happening if it isn't a clean stop at all), and state what kind of review scrutiny each case would need.

4 (Production-gear) The plan that didn't get revised

An agent working on "migrate the orders table's status column from a string to an enum" writes this upfront plan on turn 1, before any tool calls:

1. Add the new enum type in the schema
2. Update the orders model to use it
3. Write a migration script
4. Update the two call sites in orders/service.py

On turn 6, a grep_codebase result reveals four more call sites in reports/exporters.py and billing/reconcile.py that step 4 didn't account for. The transcript shows the agent updating only the original two call sites and then declaring the task done. Using this chapter's upfront-plan-vs-reactive distinction, explain specifically what should have happened at turn 6 and didn't, and why an upfront, unrevised plan is the mechanism that produced this specific gap (not "the agent was careless").

5 (Production-gear) Diagnose the tool-confusion bug

A harness exposes two tools to the model:

update_config(key: string, value: string)
  "Update a configuration value."

set_env(key: string, value: string)
  "Set an environment variable."

Given the task "increase the request timeout to 30 seconds," the agent calls set_env("REQUEST_TIMEOUT", "30"), but the timeout is actually read from a config file at startup, not an environment variable — the fix silently does nothing. Using the lesson's account of how tool selection works (no separate router, just prediction matched against tool descriptions), explain what's actually missing from these two tool descriptions that made this outcome likely, and propose a specific rewritten description for each tool that would have made the correct choice the higher-probability one.

6 (Production-gear) Build the turn-by-turn trace

You're handed this compressed summary of an agent run: "Task: fix the flaky test_checkout_total test. The agent searched for the test, read it, ran it three times to confirm flakiness, found a float-rounding issue in cart/pricing.py, read that file, made an edit using Decimal instead of float, ran the test five times to confirm it passed consistently, then stopped." Rebuild this as an actual numbered turn-by-turn trace, where each turn lists: the tool called (or "text only, no tool call" for the final turn), the argument(s), and — in your own words, tied to the mechanism, not a paraphrase of the summary — what specific new fact in context made that turn's call the most probable next action given the turn before it. Flag anywhere the compressed summary hides a decision point that the real trace would have had to make explicitly (for example: how did it know to look in cart/pricing.py specifically?).
