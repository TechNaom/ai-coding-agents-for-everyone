Chapter 11 Exercises ~45 min

Exercises: Security, Sandboxing, Permissions, Destructive Commands

These exercises don't need Ollama, a live model, or network access to verify — starter.py and solution.py in this folder rebuild the permission layer's own building blocks (a fail-closed policy lookup, the full allow/confirm/block decision flow, and a threat-category classifier) as small, testable functions.

Exercise standard Six tasks below. At least three are production-gear: harder, ambiguous, real-world judgment calls rather than clean textbook cases.

1 Implement policy_for

Open starter.py. Fill in TODO 1: a fail-closed lookup that returns BLOCKED for any tool name not explicitly present in the policy dict. Run python3 starter.py and get the first four checks to PASS.

2 Implement evaluate_call

Fill in TODO 2: the allow/confirm/block decision flow, using an injectable confirmation function and an injectable "run the tool" function instead of real stdin or real side effects. Get the next six checks to PASS.

3 Implement classify_threat

Fill in TODO 3: classify a shell command string into one of this chapter's four threat categories using keyword checks in a specific priority order. Get the remaining eight checks to PASS.

4 (Production-gear) Design a policy for a tool this chapter never covered

Your team is adding a run_database_migration(sql_file) tool to an agent that already has this chapter's permission layer. The migration runs against a real staging database (not production) but is only reversible if a DBA manually restores from a backup. Which of the three tiers (ALLOWED, REQUIRES_CONFIRMATION, BLOCKED) does this belong in, and why? Is a per-tool tier even fine-grained enough here, or does this specific tool argue for something more — e.g. a policy that also depends on which database the migration targets? Write 3-4 sentences.

5 (Production-gear) Trace what happens when stdin isn't there

A teammate deploys this chapter's agent as a scheduled cron job with no terminal attached — stdout goes to a log file, stdin is connected to /dev/null. The agent calls write_file, which is REQUIRES_CONFIRMATION. Using project/solution.py's actual confirm_with_human (read it, don't guess), trace exactly what happens: does the cron job hang forever, crash, or return a clean result? What does your answer reveal about why "fails closed on EOF" is a load-bearing design decision, not a defensive nicety, for any agent that might ever run unattended?

6 (Production-gear) Review a PR that adds a tool without updating the policy

A diff adds a new tool, run_database_query(sql), to TOOLS and TOOL_FUNCTIONS in a copy of this chapter's agent — but the PR author forgot to add an entry for it in TOOL_POLICY. Using check_permission's actual fail-closed default (not a guess about what "probably" happens), what's the real, observable behavior the very first time the model tries to call this new tool? Is this a bug worth blocking the PR over, or is the fail-closed default already doing its job here? Write 3-4 sentences explaining your answer with reference to the actual code path.
