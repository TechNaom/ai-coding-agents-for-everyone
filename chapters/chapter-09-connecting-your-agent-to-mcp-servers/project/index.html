Chapter 9 Project ~35 min · Level 3 — Independent

Project: Swap git_status/git_diff for MCP-Based Versions

This is Module 3's real Level 3 (Independent) project, per docs/curriculum/CURRICULUM_MAP.md: "build a coding agent from scratch with MCP-based tools, no scaffold." Read literally against every prior tool this course built by hand, that would mean re-deriving Chapter 8's entire file from nothing — which wouldn't actually test what this chapter teaches. What's genuinely new and independent here isn't the file layer, the denylist, or the loop; it's the MCP integration itself: opening a client connection, discovering a server's tools, and bridging them into this course's TOOLS/TOOL_FUNCTIONS shape. That's exactly the one piece this project gives you no scaffold for — connect_git_tools() in starter.py is a single unimplemented function with a full docstring explaining the task, not filled-in code with one small blank the way Chapter 8's L2 project worked.

What's provided

starter.py is Chapter 8's exact agent (read_file, write_file, edit_file, hardened run_shell_command, _safe_path, dispatch_tool_call's defensive handling, run_agent's loop) with git_status and git_diff removed as local functions. mcp_git_server.py is a separate, standalone MCP server exposing those same two tools over MCP instead — read it first, it's short. The MCPBridge class (the plumbing that lets a synchronous loop call an inherently async MCP client) is also fully provided, with a docstring explaining a real implementation pitfall this chapter's build hit and fixed. None of that is your job to write.

Your task

Implement connect_git_tools() — the one function left as a TODO. It needs to: start mcp_git_server.py as a subprocess and open an MCP client connection over stdio; call the server's list_tools() to discover what it exposes; convert each discovered tool's MCP metadata into this course's existing {"type": "function", "function": {...}} schema shape and append it to TOOLS; register each tool's name in MCP_TOOL_NAMES so the already-provided dispatch_tool_call routes calls for it to the MCP server; and strip the harness-injected workspace argument out of what the model sees, the exact MCP-flavored version of the _safe_path() boundary Chapter 8 taught for local file paths. Full detail is in starter.py's module docstring.

What "done" looks like Running connect_git_tools() directly (no model needed — see README.md for the exact command) should report a successful connection, show git_status and git_diff present in TOOLS with workspace correctly stripped from their schemas, and let dispatch_tool_call successfully call either one against a real git repository — all without touching a model at all. solution.py shows one fully worked, tested version if you want a reference — but the goal is a correct, working connect_git_tools(), not a byte-for-byte match.

Then: review your own diff

Before calling it finished, apply Chapter 3's five-question checklist to your own change — specifically question 2 (did it touch anything outside the stated boundary? did workspace actually get stripped from every discovered schema, or did you leave it in and let the model try to guess an absolute path it has no way of knowing?) and question 4 (is it consistent with the rest of the file's patterns — does a connection failure return False with a clear message, matching every other failure path in this file, or does it let an exception escape and crash the whole agent?).

Why this is the right project for right now

You've now built a loop from nothing (Chapter 7), extended a tool layer four times with real, specific failure-mode care (Chapter 8), and read this chapter's argument for why some tools are worth getting from a shared, reusable server instead of hand-rolling per project. This project is the one place in Module 3 where you write the actual bridge between "a protocol exposes tools" and "this agent's existing dispatch shape" — the piece every other file in this chapter handed you working code for everywhere else.
