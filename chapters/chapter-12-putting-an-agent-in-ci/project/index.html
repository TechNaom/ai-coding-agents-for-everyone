Chapter 12 Project ~50 min · Module 5 Lab

Project: Wire a Minimal Agent Into a CI Check

Per docs/curriculum/CURRICULUM_MAP.md, Module 5's second lab is exactly this: "wire a minimal agent into a CI check." starter.py in this folder is Chapter 11's exact permission-scoped agent, copied forward unchanged — the same TOOL_POLICY, the same confirm_with_human, the same resolved git_commit. Dropped into CI as-is, it is safe (every REQUIRES_CONFIRMATION call denies cleanly on closed stdin) but useless (it can't do a single useful write). Your job is the fix: a second, CI-specific policy, decided ahead of time, that lets the agent do real work without ever auto-answering a confirmation on its own behalf.

What's provided

Every tool from Chapter 11 (read_file, write_file, edit_file, list_directory, run_shell_command, git_status, git_diff, git_commit, send_email), plus one new tool this chapter adds: run_tests — narrow and bounded by design, taking no arguments at all, the least-privilege fix Chapter 11's own retrospective named for run_shell_command's over-privileged nature. A CI_MODE flag, read once from the ACAFE_CI_MODE environment variable at startup, is also provided — it's the harness deciding which policy applies before the model has produced a single token, not something a tool call or a runtime script can flip.

Your task

Four connected TODOs in starter.py: a CI-scratch write boundary inside write_file (TODO 1), the TOOL_POLICY_CI dict itself (TODO 2), a protected-branch check inside git_commit (TODO 3), and a wall-clock budget inside run_agent (TODO 4) so a run that thrashes in CI stops on its own instead of burning real CI minutes. Full spec in the module docstring and each TODO's own comment.

What "done" looks like Running python3 starter.py (interactive-mode demo) and ACAFE_CI_MODE=1 python3 starter.py (CI-mode demo) each run a full scripted demonstration with no live model needed. Interactive mode should behave exactly like Chapter 11 — unaffected by anything you built for CI. CI mode should show: run_tests running a real failing test suite; write_file succeeding inside ci-scratch/ but refused outside it; edit_file and run_shell_command refused outright with no prompt; git_commit succeeding on a scratch branch but refused on main; send_email refused in every mode.

Two use cases, one project

The PR review bot (demo_pr_review_bot) is already built for you, not a TODO — it's entirely read-only, and every tool it needs was already ALLOWED under Chapter 11's policy with zero changes. The CI troubleshooting agent (demo_ci_mode) is where your TODOs actually earn their keep: it runs a real, disposable git repo with a real failing test, and needs real write capability that Chapter 11's policy alone would never grant unattended.

A real, illustrative CI workflow

example-ci-workflow.yml shows how this project's two use cases would actually get wired into a real GitHub Actions job — a read-only review job that posts a PR comment, and a troubleshooting job that runs only after tests fail, works on a scratch branch under ACAFE_CI_MODE=1, and opens a draft pull request a human still has to review before merging. This file is clearly marked illustrative — it is not wired into, and does not run as part of, this course repo's own CI.

Before you call it done

Run both modes with stdin closed: python3 starter.py < /dev/null and ACAFE_CI_MODE=1 python3 starter.py < /dev/null. Confirm specifically that write_file and git_commit behave DIFFERENTLY depending on the path or branch, not just on their tier — a tool being ALLOWED in TOOL_POLICY_CI is only half the story; the scope check inside the function body is the other half, and it's the half that actually keeps this design honest.
