Part A — Multiple Choice

Choose the single best answer for each.

A1. Why does a hallucinated API call typically look just as plausible as a real one, per Chapter 10?

  • (a) Models are specifically trained to disguise incorrect code
  • (b) It's generated by the same "most probable continuation" mechanism as any other text, with no built-in check against the library's actual real source
  • (c) Hallucinated calls always use unusual variable names that give them away on close reading
  • (d) It only happens with very old, unmaintained libraries

A2. Which of the following is not one of the three situations Chapter 10 names as clustering hallucinated APIs?

  • (a) Less common libraries with less training data
  • (b) APIs that changed (renamed, removed) after the model's training data
  • (c) A call shape borrowed from a structurally similar, more common library that doesn't actually support it
  • (d) Any function call with more than two keyword arguments

A3. A diff imports a new module cleanly, with no errors. What does this actually prove?

  • (a) Every method and argument used later in the file is real
  • (b) The package is installed and its module-level code ran without error — nothing about any specific method or argument used further down
  • (c) The diff is safe to merge without further checking
  • (d) The model correctly understood the library's full API surface

A4. Per Chapter 10, why is a logical bug (like an inverted boolean condition) generally harder to catch than a hallucinated API call?

  • (a) Logical bugs are rarer, so reviewers are less practiced at spotting them
  • (b) There's no dictionary/documentation lookup that settles whether logic is correct the way hasattr() settles whether a call is real — it requires tracing actual values through the actual logic
  • (c) Logical bugs always involve more lines of code than hallucinated APIs
  • (d) Logical bugs only occur in loops, which are inherently harder to read

A5. A function has a default argument tags=[]. What's the specific mechanism that makes this a bug risk?

  • (a) Lists can't be used as default arguments in Python at all
  • (b) Python evaluates the default value once, at function-definition time, so every call that uses the default shares and can mutate the same list object
  • (c) [] is slower to initialize than list()
  • (d) Default arguments are always copied fresh per call, so this is actually never a bug

Part C — Code Review Exercise

C1. Find and explain every flaw.

Below is a small "diff" — a function delivered by an agent, claiming to fix a reported bug. The task given to the agent was: "Deduplicate a list of customer records by email address, keeping the record with the most recent last_updated timestamp for each email. Records missing an email address should be dropped, not kept. Fix in customers/dedupe.py. Acceptance: pytest tests/customers/test_dedupe.py passes." The agent reports success, and the named test passes.

customers/dedupe.py 
--- a/customers/dedupe.py
+++ b/customers/dedupe.py
@@
 def dedupe_by_email(records):
-    return records
+    seen = {}
+    for r in records:
+        email = r.get("email")
+        if email is None:
+            continue
+        existing = seen.get(email)
+        if existing is None or r["last_updated"] >= existing["last_updated"]:
+            seen[email] = r
+    return list(seen.values(exclude_none=True))

There are exactly three planted issues in this diff — at least one hallucinated API call and at least one logical bug. For each one:

  • Quote or point to the specific line.
  • State whether it's a hallucinated API or a logical bug.
  • Explain, mechanically (not just "it looks wrong"), why it's actually incorrect.
  • State what would actually happen if this code ran exactly as written, on a realistic input.

C2. Triage.

Using Chapter 3's review triage order (file list and acceptance criterion first, full attention on high-blast-radius or unusual lines, lighter skim on mechanical/expected changes), explain which of this diff's three flaws you'd expect a reviewer following that order to catch fastest, and which one is most likely to slip through a reviewer who only checks "did the named test pass."

Part C — full worked answer key:

The diff has exactly three planted flaws (plus one line included to test whether you over-flag something defensible):

  1. Hallucinated API — seen.values(exclude_none=True). dict.values() takes no arguments at all, in any Python version — it is not possible to pass exclude_none (or anything else) to it. This raises TypeError: dict.values() takes no keyword arguments the instant this line runs (verified against a real Python interpreter). It's the near-miss category the lesson describes: exclude_none sounds like a reasonable thing a "clean" API might support, especially since the function already filters None emails a few lines above — but dict.values() simply has no such option, and the filtering the diff wants is already fully handled by the earlier if email is None: continue line, making this hallucinated argument not just wrong but entirely redundant even in concept.
  2. Logical bug — r["last_updated"] (and existing["last_updated"]) will raise KeyError on any record missing that key. The acceptance criterion only requires records missing an email to be dropped — nothing in the task says every remaining record is guaranteed to have last_updated present. If any record reaches the comparison line without a last_updated key, this raises KeyError instead of a graceful skip or a sensible default. Whether this actually fires depends entirely on whether the named test's fixture data happens to include a record missing that field — exactly the kind of untested-path risk Chapter 10's average_order_value example demonstrates.
  3. Logical bug — only email is None is treated as "missing," not an empty string. The task says "records missing an email address should be dropped, not kept." A record with "email": "" is not None, so r.get("email") returns "", which is not None, so the record is NOT dropped — it gets treated as a valid (if unusual) dedup key instead. Whether this counts as "missing" is genuinely a judgment call the task's own wording leaves ambiguous, but a careful reviewer should at minimum flag it as a gap between the stated intent ("missing... should be dropped") and what the code actually checks for (is None only), and ask the author or the ticket which behavior was actually intended.

Not a required flaw — >= instead of > on the tie-break. Using >= here (keep the later record on an exact timestamp tie) is a defensible, arguably correct choice for "keep the most recent," not a bug on its own — there's no stated requirement about tie-breaking behavior, so there's nothing to check it against. A correct C1 answer should recognize this is very likely intentional and defensible rather than reflexively flagging every comparison operator in the diff — the same over-flagging risk the chapter's own project's round() example tests for.

A strong C1 answer identifies flaw 1 confidently (checkable by running the exact call, or reasoning that dict.values() accepts no arguments), traces flaw 2 to a concrete example record missing last_updated to show the KeyError, and explicitly notes flaw 3 as a gap between stated intent and actual check (not just "this could be better") — while correctly declining to flag the >= tie-break as a bug.

C2 (self-check): Chapter 3's triage order would likely catch flaw 1 fastest — it's on a genuinely unusual line (.values(exclude_none=True) isn't a pattern the rest of a typical codebase would already use, making it a natural "spot-check against the codebase's real pattern" catch). Flaw 2 (the missing-last_updated KeyError risk) is the one most likely to slip through a reviewer who only checks "did the named test pass" — if the test fixture happens to give every record a last_updated value, the acceptance check passes cleanly while the crash risk on real, messier production data goes completely unverified, exactly the "passes the check on a technicality" gap Chapter 3's question 1 was built to catch. Flaw 3 (empty-string email) sits in between: it requires actually reading the task's exact wording against the exact condition in the code, not just running anything.

Part D — self-check, not a published key. A strong answer proposes something concrete and specific — for example, a CI step that greps diffs for newly-introduced method calls on standard-library or well-known third-party types and runs each one against the actual installed library/type in isolation before merge (would catch flaw 1 mechanically, would NOT catch flaws 3-4 since those require realistic test data, not just call-existence checking), or a review-checklist line requiring the author to name which fields every accessed key (like last_updated) is actually guaranteed to have, and by what (would catch flaw 3-4's assumption directly, would NOT catch a hallucinated API on a line nobody thought to flag as "accessing a field"). The honest-gap requirement matters: an answer that claims one mechanism catches everything hasn't fully understood that hallucinated APIs and logical bugs require different verification strategies, per Chapter 10's interview question 6.
