Chapter 1 Practice Bank ~20 min

Practice Bank: Why Coding Agents Aren't Just Autocomplete

Short scenarios, one judgment question each — practice telling loop-driven agent behavior apart from single-shot prediction in realistic, sometimes ambiguous situations.

Scenario · New hire

The onboarding assumption

A new hire says "I've used Copilot for two years, so agent mode should feel exactly the same, just with a chat box." What's the one expectation you'd correct before their first real task with an agent, and why does it matter for that first task specifically?

Scenario · Debugging

The silent multi-file fix

An engineer asks an agent to "fix the flaky login test." The agent comes back having edited the test file and a shared fixture used by four other test files. The engineer is surprised the fixture changed at all. Using the plan/act/observe loop, explain how that fixture edit plausibly happened without the agent going rogue.

Scenario · Estimation

The time-savings pitch

A team lead pitches "coding agents will save us 50% of dev time because they're just faster autocomplete." What's misleading about framing the value this way, based on what you now know actually changed (loop and tool use, not raw prediction speed)?

Scenario · Trust

The "it ran the tests, so it's fine" trap

An agent reports "all tests pass" after a multi-file change. A reviewer approves the PR on that basis alone. What does "tests pass" actually verify about an agent-driven change, and what does it not verify — especially compared to a change a human made one line at a time with inline suggestions?

Scenario · Tool choice

The wrong tool for a tiny task

A developer fires up an autonomous coding agent to rename one local variable across a single 20-line function they already have open. It works, but takes noticeably longer than just typing the rename with inline-suggestion help. What does this suggest about when the agent loop's overhead is worth paying, versus when it isn't?

Scenario · Incident review

The compounding misread

During an incident postmortem, someone notes the agent misinterpreted an early test failure, "fixed" the wrong file, then observed a second failure and made a second wrong edit before a human caught it. Where in the plan/act/observe/repeat loop did this go wrong, and is this a failure mode autocomplete-style tools could have produced in the same way?
