Chapter 8 Exercises ~40 min

Exercises: Giving Your Agent File/Shell/Git Tools

This chapter's exercises don't need a running Ollama server to verify — starter.py and solution.py in this folder test edit_file's ambiguous-match-refusal logic and run_shell_command's denylist check against an in-memory fake filesystem and a set of scripted commands, so every exercise below is checkable by running the file directly.

Exercise standard Six tasks below. At least three are production-gear: harder, ambiguous, real-world judgment calls rather than clean textbook cases.

1 Implement edit_file_stub

Open starter.py. Fill in TODOs 1 through 4 inside edit_file_stub: reject a missing file, reject a zero-match find string, reject an ambiguous (more than one match) find string, and otherwise perform the replacement. Run python3 starter.py and get the first five checks to PASS.

2 Implement is_command_blocked

Fill in TODOs 1 through 3 inside is_command_blocked: check a command string against every pattern in DENYLIST and return the matching reason, or None if nothing matches. Get the remaining four checks to PASS.

3 Trace a real failure by hand

Without running any code, write out step by step what edit_file_stub("dup.py", "return None", "return 0") actually returns and why — name each line of your implementation that gets triggered, in order, including what count equals at the point the ambiguous-match branch fires. Then run it and confirm your trace was right.

4 (Production-gear) Add a new denylist pattern without touching the checking logic

A real incident: someone ran chmod -R 777 . inside a shared workspace, making every file world-writable. Add a new (pattern, reason) pair to DENYLIST in starter.py that would have blocked this exact command, plus two new test cases in main() — one that confirms the dangerous form is blocked, and one that confirms an unrelated, legitimate chmod call (e.g. chmod +x script.sh) is NOT blocked by your new pattern. If your pattern is too broad and blocks the legitimate case too, that's exactly the false-positive cost the lesson's allowlist-vs-denylist discussion warned about — tighten it until both cases pass.

5 (Production-gear) Construct a find string that's ambiguous by exactly one character

Add a new entry to FAKE_DISK and pick a find string such that it matches exactly twice in your new file's content, but a one-character-longer version of the same string (more surrounding context) matches exactly once. Write both calls to edit_file_stub, predict both outcomes before running, then verify. This mirrors a genuinely common real mistake: a find string that's technically correct but too short to be unique.

6 (Production-gear) Review a hypothetical git_commit design

A coworker proposes this: git_commit(message) is added as a tool, and the harness code (not the model) always passes a hardcoded, harness-controlled message prefix like "[agent] " before whatever the model wrote, arguing this makes autonomous commits "traceable and therefore safe." Using this chapter's distinction between what the model controls and what the harness enforces, explain in 2-3 sentences why traceability (knowing which commits came from the agent) is a different property from safety (preventing a bad commit from happening at all), and what's still missing from this design even with the prefix in place.
