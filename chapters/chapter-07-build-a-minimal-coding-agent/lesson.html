The Model: Ollama, llama3.2, and What It Costs in Hardware

Every prior chapter's code examples, where they existed at all, were illustrative — JSON shapes and pseudocode meant to be read, not run. This chapter's code calls a real model, which means it needs a real model to call. This course's default is Ollama, a program that runs an open-source model entirely on your own machine — no account, no API key, no per-call cost to anyone, because nothing ever leaves your computer.

The model this chapter's code was actually tested against is llama3.2 — a 3-billion-parameter model, about a 2GB download, with confirmed tool-calling support. It runs on modest hardware: expect to need roughly 4GB of free RAM while it's loaded and about 2GB of free disk for the model weights themselves — a machine that can comfortably run a browser with a dozen tabs open can run this. That's the direct replacement for what earlier drafts of this course would have stated as a dollar-cost: with a fully local model, the real cost moved from "money per API call" to "RAM and disk on your own machine," and it's worth stating plainly rather than glossing over.

What is... a tool-calling-capable model, and why does that matter here? Not every model a tool like Ollama can run supports structured tool calls at all — some only ever produce plain text, no matter how you prompt them. llama3.2 was specifically chosen and tested here because Ollama lists it with confirmed tools capability. If you want a stronger model for coding-specific tasks and have more RAM/disk to spare, qwen2.5-coder is worth trying — it's a reasonable candidate for this same setup, but unlike llama3.2, its tool-calling behavior was not independently re-verified for this chapter, so treat it as a documented next step to try yourself, not a claim this chapter is making on your behalf.
setup.sh 
# 1. Install Ollama: https://ollama.com (macOS, Linux, Windows)
# 2. Pull the model this chapter uses:
ollama pull llama3.2
# 3. Make sure the server is running (often starts automatically):
ollama serve
# 4. Install the one Python dependency this chapter needs:
pip install openai

That last line is worth pausing on: this course does not use Ollama's own Python package, and it does not use any third-party agent framework. It uses the plain openai Python package — the same client library people use to call OpenAI's hosted API — pointed at Ollama's local server instead. Ollama exposes a genuine OpenAI-compatible /v1/chat/completions endpoint, so the same client that knows how to talk to OpenAI's API can talk to your own machine instead, just by changing where it connects:

the one line that decides where this agent's brain lives 
from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
# api_key is a required placeholder here -- Ollama doesn't check it,
# but the client library requires something non-empty to be passed.

Every tool call, every message, every part of the loop below flows through this one client object. Section 7 of this chapter comes back to this exact line and shows you how to point it at a real hosted provider instead, if you ever want to — the rest of the agent's code doesn't change at all.

The Tools: read_file, write_file, run_shell_command

Chapter 4 explained that a tool is described to the model as a name, a plain-language description, and a schema for its arguments — and that description is the only thing that tells the model the tool exists at all. This chapter deliberately keeps the toolset to exactly three: enough to make a genuinely working coding agent, not so many that the tool layer itself becomes the subject (Chapter 8 is specifically about going deeper on file/shell/git tools — this chapter's job is the loop, not tool breadth).

the tool schemas the model actually sees 
TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "read_file",
            "description": "Read the full contents of a text file, given a path relative to the workspace.",
            "parameters": {
                "type": "object",
                "properties": {
                    "path": {"type": "string", "description": "Path relative to the workspace root"}
                },
                "required": ["path"],
            },
        },
    },
    {
        "type": "function",
        "function": {
            "name": "write_file",
            "description": "Write text content to a file, given a path relative to the workspace. Overwrites the file if it exists, creates it if not.",
            "parameters": {
                "type": "object",
                "properties": {
                    "path": {"type": "string", "description": "Path relative to the workspace root"},
                    "content": {"type": "string", "description": "The full text content to write"},
                },
                "required": ["path", "content"],
            },
        },
    },
    {
        "type": "function",
        "function": {
            "name": "run_shell_command",
            "description": "Run a shell command inside the workspace directory and return its stdout, stderr, and exit code.",
            "parameters": {
                "type": "object",
                "properties": {
                    "command": {"type": "string", "description": "The shell command to run"}
                },
                "required": ["command"],
            },
        },
    },
]

A schema alone doesn't do anything — it's a description handed to the model. The real function it maps to is where Chapter 4's "harness" stops being an abstraction. Every one of these three functions is confined to a single WORKSPACE directory, using one shared helper that rejects any path trying to climb out of it:

the real functions the tool calls actually run 
import os, subprocess

def _safe_path(path):
    """Reject any path that would resolve outside the workspace directory."""
    full = os.path.abspath(os.path.join(WORKSPACE, path))
    if not full.startswith(os.path.abspath(WORKSPACE) + os.sep) and full != os.path.abspath(WORKSPACE):
        raise ValueError(f"path escapes workspace: {path}")
    return full

def read_file(path):
    try:
        with open(_safe_path(path)) as f:
            return f.read()
    except FileNotFoundError:
        return f"error: no such file: {path}"

def write_file(path, content):
    full = _safe_path(path)
    os.makedirs(os.path.dirname(full), exist_ok=True)
    with open(full, "w") as f:
        f.write(content)
    return f"wrote {len(content)} bytes to {path}"

def run_shell_command(command):
    result = subprocess.run(
        command, shell=True, cwd=WORKSPACE, capture_output=True, text=True, timeout=15
    )
    return json.dumps({"stdout": result.stdout, "stderr": result.stderr, "exit_code": result.returncode})

_safe_path is a boundary in exactly Chapter 2's sense, implemented as real code instead of an instruction hoped the model follows: it doesn't matter what the model asks for, a path like "../../etc/passwd" or an absolute path outside WORKSPACE gets rejected before any file operation happens, independent of the model's intent. This is also a preview of Module 5's security material — a harness-enforced boundary, not a model-trusted one — kept minimal here on purpose; Chapter 11 covers permission scoping and destructive commands in real depth.

The Loop: Calling the Model, Dispatching, Repeating

Everything above is inert until something calls the model, reads what it produced, and — if it's a tool call — actually runs the right function and feeds the result back. That's the entire loop, and it's short enough to read in one pass:

the plan/act/observe/repeat loop, as real code 
MAX_STEPS = 8  # Chapter 4's hard stop, made concrete

def dispatch_tool_call(tc):
    """Turn one tool_use block into a real function call. Never raises."""
    name = tc.function.name
    try:
        args = json.loads(tc.function.arguments)
    except json.JSONDecodeError:
        return f"error: invalid JSON arguments: {tc.function.arguments!r}"

    if name not in TOOL_FUNCTIONS:
        return f"error: unknown tool: {name}"

    try:
        return TOOL_FUNCTIONS[name](**args)
    except KeyError as e:
        return f"error: missing required argument {e} for {name}"
    except Exception as e:
        return f"error: tool {name} failed: {e}"


def run_agent(task, client):
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": task},
    ]

    for step in range(1, MAX_STEPS + 1):
        response = client.chat.completions.create(model=MODEL, messages=messages, tools=TOOLS)
        msg = response.choices[0].message
        messages.append(msg)  # confirmed: the raw message object appends directly

        if not msg.tool_calls:
            print(f"[clean stop after {step} step(s)]")
            print(msg.content)
            return messages  # Chapter 4's clean stop

        for tc in msg.tool_calls:
            result = dispatch_tool_call(tc)
            messages.append({"role": "tool", "tool_call_id": tc.id, "content": str(result)})

    print(f"[step cap reached after {MAX_STEPS} steps without a clean stop]")
    return messages  # Chapter 4's hard stop

Read this against Chapter 4's own language and it should feel like a direct translation, because it is one. "Plan" is the model's prediction inside chat.completions.create — nothing about picking the next step lives anywhere else; there's no separate planning module. "Act" is dispatch_tool_call actually invoking a real Python function with real side effects. "Observe" is messages.append({"role": "tool", ...}) — literally placing a new block of text into the conversation the model will read whole again on its very next call, exactly as Chapter 4 described it: the model has no persistent awareness of the function having run, only a new message it reads from scratch. "Repeat" is the for step in range(...) loop itself. And the two return statements are Chapter 4's clean stop and hard stop, named in comments at the exact lines that implement them, with the other three stop conditions (boundary, failure, context-limit) available to add on top of this same shape once you need them — a boundary stop is one more if name in BLOCKED_TOOLS: return check before dispatch; a failure stop is one more branch in dispatch_tool_call's exception handling that decides some errors should end the loop instead of just being reported back.

What is... the system prompt doing here? SYSTEM_PROMPT is the very first message in messages, present on every single call, and it's the only place this agent states its own rules in plain language: "you have three tools," "paths are relative to the workspace," "reply with plain text and no tool call when done." Nothing about the loop's code enforces those rules directly — they're stated to the model the same way any instruction is, and the model's tool-selection behavior (Chapter 4, section 3) is what makes them matter in practice. The one thing that is code-enforced, not just requested, is _safe_path — worth noticing which kind of "rule" each piece of this file actually is.

Try it yourself with a handful of different tasks — deleting or corrupting a file it wrote earlier in the same session is a good one for watching an observation genuinely redirect the next step, the same way Chapter 4's rate-limiting example did.

A Small Model's Tool Calls Aren't Always Clean — Defend Against That

Here's an honest finding from testing this exact chapter's code, not a hypothetical: on one run, llama3.2 produced a tool call with an incomplete or wrong arguments object — a required key the schema demanded simply wasn't present — and then produced a correct one on a retry with identical input. Nothing about the prompt changed between attempts. This is a real, measurable property of small local models: they're less reliable at clean tool-call argument formatting than the largest hosted models, and a minimal agent's code has to be written assuming that will happen sometimes, not treating it as a rare edge case to shrug off.

This connects directly to Chapter 5's premature-done and going-off-the-rails failure modes: code that assumes args["path"] always exists because the schema said it was required is code that trusts the model's own text the way Chapter 5 warned against trusting a clean stop's confidence. Look back at dispatch_tool_call above — this is exactly why it has three separate failure branches instead of one happy path:

the same three lines, isolated 
    except json.JSONDecodeError:
        return f"error: invalid JSON arguments: {tc.function.arguments!r}"
    ...
    except KeyError as e:
        return f"error: missing required argument {e} for {name}"

Both catch a specific, real way the model's output can fail to match its own schema — malformed JSON entirely, or valid JSON missing a key the schema marked required. Neither one lets an exception propagate up and kill the loop. Instead, the failure becomes a tool result like any other — a text block telling the model exactly what went wrong, appended to the conversation the same way a successful result would be. Concretely, that means the model gets a real chance to see "missing required argument 'path'" on its next turn and correct itself, the same self-correcting dynamic Chapter 4 described for any other observation — instead of the whole agent crashing on an ungraceful KeyError traceback the first time a small model has an off turn. Larger hosted models make this mistake less often, but "less often" is not "never," and a minimal agent that only works when the model's output happens to be perfect isn't actually minimal — it's fragile.

Using a Hosted API Instead

This course's own build stays free and open-source by default — Ollama, running entirely on your machine, zero API key, zero cost per call. But because OpenAI, Anthropic, and Google Gemini all expose an endpoint that speaks the same request/response shape as the openai client, pointing this exact agent at a hosted provider instead is a base_url/api_key/ model change, not a rewrite. Every line of TOOLS, every tool function, dispatch_tool_call, and run_agent above is completely unaffected — only the three lines that construct client and pick MODEL change. If you try any of these, remember: unlike Ollama, each one needs a real account and a real API key from that provider, and each call costs real, small amounts of money — check that provider's current pricing page before running anything at scale, since the numbers below are current as of this writing and providers change them.

Swap 1 — OpenAI
diff against the Ollama baseline 
- client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
- MODEL = "llama3.2"
+ client = OpenAI(api_key=os.environ["OPENAI_API_KEY"])  # base_url defaults to OpenAI's own API
+ MODEL = "gpt-4o-mini"

OpenAI's client already defaults to OpenAI's own API when you don't pass a base_url at all — this is the "home" endpoint the openai package was originally built for, so nothing else in the agent changes. gpt-4o-mini is a genuinely low-cost model in OpenAI's current lineup, priced (as of this writing) around $0.15 per million input tokens and $0.60 per million output tokens — a single small agent task like the ones this chapter ran costs a small fraction of a cent, but it is a real, metered cost tied to a real API key, not the free default.

Swap 2 — Anthropic (Claude), via its OpenAI-compatible endpoint
diff against the Ollama baseline 
- client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
- MODEL = "llama3.2"
+ client = OpenAI(api_key=os.environ["ANTHROPIC_API_KEY"], base_url="https://api.anthropic.com/v1/")
+ MODEL = "claude-sonnet-4-6"

Verified directly against Anthropic's current OpenAI SDK compatibility docs while writing this section: the endpoint is real, tool calls (tools, tool_calls in the response, role: "tool" results) are fully supported through it, and the request/response shape this agent's code already uses maps over cleanly. Anthropic's own documentation is explicit that this compatibility layer is meant for testing and evaluating Claude against existing OpenAI-shaped code, not as their recommended long-term production path — for production use of Claude specifically, Anthropic points people at their native API instead. For this chapter's purpose (proving the same agent code works against a different provider with a three-line change) it's exactly the right tool. Pricing for a mid-tier Claude model like this is around $3 per million input tokens and $15 per million output tokens as of this writing — noticeably more per token than the OpenAI option above, so check current numbers for whichever specific Claude model you pick.

Swap 3 — Google Gemini, via its OpenAI-compatible endpoint
diff against the Ollama baseline 
- client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
- MODEL = "llama3.2"
+ client = OpenAI(api_key=os.environ["GEMINI_API_KEY"], base_url="https://generativelanguage.googleapis.com/v1beta/openai/")
+ MODEL = "gemini-3.1-flash-lite"

Verified directly against Google's current Gemini OpenAI compatibility docs while writing this section: Google publishes this exact .../v1beta/openai/ path specifically so the openai client can talk to Gemini models unmodified, and function/tool calling is documented as fully supported through it using the same schema shape this agent's TOOLS list already uses. A lightweight Gemini Flash model is a genuinely low-cost option here too — current pricing for the smallest Flash-Lite tier is roughly $0.25 per million input tokens and $1.50 per million output tokens, in the same ballpark as OpenAI's cheapest option above. As with both swaps above, treat the exact price as something to re-check on the provider's own pricing page, not a number this chapter guarantees will still be current when you read it.

Notice what didn't need to change in any of the three diffs above: TOOLS, read_file/write_file/ run_shell_command, dispatch_tool_call, and run_agent's entire loop. That's the practical payoff of building this agent against the plain openai client shape instead of a provider-specific SDK from the start: the mechanism this whole course has been teaching — tool calls as structured output, a harness that actually executes them, a loop that stops on one of Chapter 4's conditions — isn't tied to any one company's product. It's a property of how the request/response shape works, and four different providers (Ollama included) all speak close enough to the same shape that the same 80 lines of Python work against any of them.

GenAI Builder Thought Process

Problem: a developer who's followed Chapters 4 through 6 conceptually sits down to actually write an agent loop and reaches for a framework — an agent SDK, a "batteries included" library — assuming the loop itself must be complicated enough to need one.

Assumption being made: that "the loop" is a large, delicate piece of infrastructure, and that hand-writing it risks getting something subtly wrong that a maintained library would have handled correctly.

What actually distinguishes it: the loop this chapter built is under thirty lines — a for loop, one API call, one if checking for tool calls, one nested loop dispatching them, two return statements. Every piece of apparent complexity in "building an agent" turns out to live in the tool layer (what real functions exist, how carefully they're scoped) and in defensive handling around the model's output (Section 6's JSON/KeyError handling), not in the loop's control flow itself. A framework mostly packages up decisions about the tool layer and defensive handling that you can and, while learning, probably should make yourself first.

Why this matters before Chapter 8: Chapter 8 goes deeper on the tool layer specifically — more file operations, real git integration, more careful shell-command handling. None of that changes the loop you just built; it only adds more entries to TOOL_FUNCTIONS and more schemas to TOOLS. Understanding that the loop and the tool layer are separable pieces — one short and stable, the other where real engineering effort goes — is the single most useful mental model to carry into that chapter.

Working definition to carry forward: a minimal coding agent is a short, boring control-flow loop wrapped around two things that actually deserve care: a small set of real, safely-scoped tools, and defensive handling that assumes the model's output won't always perfectly match its own schema. The loop itself is not the hard part, and shouldn't be treated like it is.

Points To Remember

  • This chapter's agent is built from scratch against the plain openai Python package, pointed at Ollama's local OpenAI-compatible endpoint (base_url="http://localhost:11434/v1", a placeholder api_key) by default — no third-party agent framework, no Anthropic API dependency in the default path, zero cost per call, using llama3.2 (~2GB download, roughly 4GB RAM to run) as the tested, confirmed tool-calling-capable model.
  • A tool is a schema (name, description, argument shape) plus a real Python function; the harness — not the model — is what actually executes it and enforces boundaries like _safe_path's workspace confinement, independent of what the model asks for.
  • The loop is a direct translation of Chapter 4's mechanism: one API call per turn (plan, via prediction), tool dispatch (act, real side effects), appending the result (observe, a new message the model reads fresh next turn), and a for loop (repeat) that ends on a clean stop (no tool call) or a step cap (Chapter 4's hard stop) — with boundary and failure stops addable in the same shape once needed.
  • A small local model's tool-call arguments won't always perfectly match their schema — this was directly observed while testing this chapter's own code, not assumed. Defensive handling (catching json.JSONDecodeError and KeyError, returning a descriptive error string instead of crashing) is required discipline, not optional polish, and it's the same "don't trust the model's own confident output at face value" instinct Chapter 5 taught for premature "done."
  • Because Ollama, OpenAI, Anthropic, and Gemini all speak close enough to the same request/response shape, swapping this agent to a hosted provider is a three-line change to client and MODEL — everything else, including the entire loop and tool layer, is untouched. Each hosted option costs real, small amounts of money per call and needs a real API key, unlike the free local default.
  • The loop's control flow is short and stable; real engineering effort goes into the tool layer and defensive handling around the model's output, not the loop itself — the mental model Chapter 8 builds on directly.
