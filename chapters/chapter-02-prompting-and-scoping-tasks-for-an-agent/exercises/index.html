Chapter 2 Exercises ~28 min

Exercises: Prompting and Scoping Tasks for an Agent

Still conceptual — no SDK or code execution yet, that starts in Module 3. These exercises build the judgment to write and evaluate prompts that give an agent the right amount of context and the right size of task.

Exercise standard Six tasks below. At least three are production-gear: harder, ambiguous, real-world judgment calls rather than clean textbook cases.

1 Rank the three prompts

Here are three prompts for the same task — adding pagination to an existing API endpoint that currently returns every row at once: (A) "add pagination to the users endpoint"; (B) "In `api/users.py`, the `list_users` endpoint returns every row with no limit. Add `limit`/`offset` query params, default `limit=50`, max `limit=200`. Update the existing test file. Acceptance: a request with no params returns 50 rows and a `next_offset` field, `pytest tests/api/test_users.py` still passes."; (C) "Please completely refactor `api/users.py` to be more RESTful and add pagination and better error handling and maybe caching if it makes sense." Rank them best to worst for how well-scoped they are, and justify the ranking using this chapter's three ingredients (context, scope, acceptance criterion) — not just a gut feeling.

2 Find the missing ingredient

This prompt is close but flawed: "In `billing/invoices.py`, fix the rounding error in `calculate_total`. Don't touch anything else." Identify the one ingredient from this chapter (context, scope boundary, or acceptance criterion) that's missing, and write the one sentence you'd add to fix it.

3 Trim the over-stuffed prompt

You're handed a 400-word prompt for a coding agent that includes: the bug symptom, the file to look at, a full company history of why the module was built that way, two unrelated tickets pasted in for "context," a boundary on what not to touch, and an acceptance criterion. Identify which parts serve one of the three jobs of context (locate the problem, know what correct looks like, know what's off limits) and which parts are padding that should be cut.

4 (Production-gear) The reasonable-sounding trap

A teammate proposes this prompt: "Clean up the error handling in `payments/gateway.py` and fix any related issues you notice." It sounds like ordinary diligence, not recklessness. Explain specifically why it's still an open-ended, unbounded mandate despite sounding reasonable, and rewrite it into a well-scoped version that preserves the intent (improve error handling) but adds a boundary and an acceptance condition.

5 (Production-gear) No clean acceptance condition

You need an agent's help with a task that has no obvious mechanically checkable acceptance condition: "improve the readability of this 200-line function without changing its behavior." There's no single test that proves "readability" improved. Propose a way to scope this prompt so the agent still has something concrete to aim for and a human still has something concrete to check, even without a pass/fail test.

6 (Production-gear) Set the boundary, justify the blast radius

You're scoping a task: "add a new field to the user profile API response." The user table is shared by three other services, and there's a caching layer in front of the API that would need invalidating if the response shape changes. Write the boundary clause you'd add to the prompt (what the agent must stop and ask about before touching), and justify it in terms of blast radius — not just "better safe than sorry."
