Chapter 10 Practice Bank ~28 min

Practice Bank: Detecting Hallucinated APIs and Logical Bugs

A runnable script (starter.py / solution.py in this folder) hands you six small snippets, each with one deliberate flaw spanning this chapter's categories. Predict, then run, then work through the six scenarios below, which extend the same discipline to situations the script's snippets don't cover.

Scenario · Untested branch

The hallucinated call in the error-handling path

A diff adds a new except block that calls logger.warn_and_continue(message) when a network request fails. Every existing test passes, because none of them actually trigger a network failure. Using this chapter's mechanical checks, how would you verify whether warn_and_continue is real without waiting for a production outage to find out? (Python's real logging.Logger has warning() — note the different name — but no warn_and_continue.)

Scenario · The confident docstring

A docstring that explains a method that doesn't exist

A function's docstring reads: "Uses Path.copy_into(dest) to move the file efficiently, avoiding a full read into memory." The explanation is detailed and sounds like it understands filesystem performance well. pathlib.Path has no copy_into method. Why does a detailed, technically- literate-sounding explanation NOT make this more likely to be real, and what specifically should you check instead of reading the explanation again more carefully?

Scenario · Version drift

The API that used to exist

A diff calls collections.Counter.most_common_unique(n). A teammate says "that's real, I've used it before" and is genuinely not lying — they're thinking of a similar-sounding helper from a different library they used on a past project. What does this scenario suggest about relying on a human teammate's memory as a substitute for the mechanical check this chapter teaches, given that a confident human can be wrong in the exact same shape a model can?

Scenario · Passes on the happy path

The discount function that only gets tested with round numbers

A function computing a loyalty discount is tested with orders of $100 and $200, and both produce correct-looking results. The function contains discount = price * 0.1 if price > 100 else 0 where the intended rule was "10% off orders of $100 or more." Using a boundary-tracing approach (not a guess), what does this function actually return for an order of exactly $100, and why do round test numbers like $100 and $200 make this kind of off-by-a-comparison-operator bug easy to miss?

Scenario · Over-flagging

The line that looks suspicious but is actually fine

A reviewer flags total = round(subtotal + tax, 2) in a currency-formatting function as "probably an agent trying to hide a bug," recalling Chapter 3's rounding-bug hook. But this particular function is the LAST step before writing a value to a UI label meant to display two decimal places, with the actual monetary calculation and storage happening earlier in Decimal arithmetic elsewhere in the file. Is the reviewer's pattern-match justified here? What's the cost of treating every use of a pattern that was once part of a real bug as automatically suspicious?

Scenario · Two flaws, one diff

When a hallucinated API AND a logical bug show up in the same three lines

A three-line diff both calls a nonexistent list.unique() method (real Python has no built-in dedup method on list at all — you'd use set() or a comprehension) AND, in the next line, uses >= where the stated intent needed >. Which of the two would you expect a reviewer relying only on "does it run" to catch, and which would survive that check entirely? What does this suggest about needing BOTH of this chapter's checks on every diff, not just one or the other?
